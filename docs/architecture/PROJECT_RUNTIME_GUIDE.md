## 1. Продуктовые правила, согласованные с владельцем

**Вкладка – это проект.** Все молекулы, расчёты и результаты принадлежат проекту независимо от выбранного раздела и от того, открыто ли окно программы. Компас редактирует структуры, Секстант запускает расчёты, Спектр показывает результаты и выполняет анализ. Общий список молекул доступен во всех трёх разделах. Атлас работает отдельно.

Проект создаётся автоматически при открытии одной или нескольких молекул. Диалог создания проекта не нужен. При открытии одного файла название берётся из имени файла, включая файл с множеством структур. Команда «Добавить молекулы» и перетаскивание в существующую вкладку дополняют её проект. Открытие через «Открыть файл» создаёт новый проект; открытие файла самого проекта подключает существующий. Для однозначности интерфейс явно различает области перетаскивания «Добавить в этот проект» и «Открыть новым проектом».

Если к исходной одиночной молекуле добавляют другие, проект получает рабочее название «Новый проект». Для явно переименованного пользователем проекта имя сохраняется. Пустая вкладка становится черновым проектом при первой добавленной или нарисованной молекуле. До этого она может быть только пустым экраном: пустые папки при каждом запуске создавать не требуется.

Папка по умолчанию: **`~/Documents/Azimuth/Проекты`**. В настройках можно выбрать другой корень. Каждому проекту соответствует отдельная подпапка с понятным именем; коллизии решаются суффиксами «(2)», «(3)». Постоянный `project_id` хранится внутри проекта и не зависит от названия или пути. Автоматический проект сразу получает постоянную папку, а не каталог ОС для временных файлов. Признак «черновик» означает, что пользователь ещё не подтвердил имя; данные уже сохраняются для восстановления.

«Сохранить» фиксирует текущее рабочее состояние и при необходимости имя. Изменение имени в интерфейсе не требует физического переименования папки. «Перенести проект» и «Создать копию» – отдельные операции с правилами из раздела 11.

**Готовые молекулы доступны немедленно.** Завершение одной молекулы не ждёт окончания всего пакета. После получения и проверки нужных файлов пользователь может открывать её плотность, орбитали и запускать QTAIM, пока остальные молекулы считаются. Завершение фонового задания не переключает выбранную молекулу, раздел или открытый анализ.

Особое научное ограничение: одинаковая молекулярная формула сама по себе не доказывает, что структуры – конформеры. Текущую эвристику `queue_of_conformers` не следует превращать в контракт новой модели. Назначение пакета и происхождение структур задаются явно.

## 3. Архитектура и направление зависимостей

Рекомендуется модульный монолит: один настольный процесс, отдельные фоновые исполнители и постоянное хранилище каждого проекта. Отдельный сервер управления Azimuth на первом этапе не требуется. Удалённая часть выполняется средствами SSH, SLURM и небольших сопровождающих скриптов.

```text
Компас / Секстант / Спектр / общий список проектов
                      |
             команды и снимки состояния
                      |
              ApplicationController
                      |
       ProjectSession (по одной на project_id)
          |              |              |
   ProjectRepository  RunCoordinator  AnalysisCoordinator
          |              |              |
     БД и файлы       ExecutionBackend  анализ / Multiwfn
                         |
                   Local / SSH + SLURM

RecoveryCoordinator подключает сохранённые проекты и задания.
Фоновые события адресуются ID, а не текущей вкладке окна.
```

`ProjectSession` отвечает за рабочие состояния молекул, состав проекта, выбранные результаты и операции сохранения. `RunCoordinator` управляет запуском и наблюдением, но не выбирает молекулу в интерфейсе. `AnalysisCoordinator` планирует QTAIM и другие обработки независимо от очереди квантово-химических расчётов. `ProjectRepository` единственный изменяет постоянные метаданные.

Чистые модели и прикладные операции не импортируют Qt, `Studio` и виджеты. Адаптер UI переводит команды и события в вызовы Qt; обновление виджетов происходит в главном потоке. SSH, процессы, чтение больших файлов и анализ работают вне главного потока. Существующие примеси можно сохранять на переходный период, последовательно делегируя их работу новым компонентам.

| Данные | Владелец | Что видит интерфейс |
|---|---|---|
| Список молекул, порядок, названия | ProjectSession / Repository | Снимок списка и ID выбранной записи |
| Несохранённые координаты и настройки | WorkingMolecule в ProjectSession | Редактируемая проекция, номер ревизии |
| Исходные данные отправленной попытки | Неизменяемый InputSnapshot | Просмотр исходных данных попытки |
| Состояние удалённого выполнения | RunCoordinator с сохранением в Repository | Последнее подтверждённое состояние и актуальность сведений |
| Файлы и результаты | ArtifactStore / ResultRecord | Доступные свойства и причина недоступности остальных |
| Камера, раскрытые панели, прокрутка | WorkspaceState | Только представление; не источник научных данных |

## 4. Модель данных и идентичность

Все идентификаторы генерируются до внешних действий. Название, номер строки, Python `id()` объекта, номер вкладки и путь к файлу не используются как идентичность молекулы или попытки. Время хранится в UTC, но порядок ревизий задаётся счётчиком, а не точностью часов.

| Сущность | Минимальные поля и связи |
|---|---|
| Project | `project_id`, `schema_version`, `name`, `revision`, порядок молекул |
| Molecule | `molecule_id`, `project_id`, название, роль, происхождение, рабочая/сохранённая ревизия |
| StructureRevision | Неизменяемые атомы и их порядок, связи, координаты и единицы, формальные заряды, ограничения; hash |
| CalculationPlan | `calculation_id`, `molecule_id`, назначение, настройки и семейство попыток |
| Attempt | `attempt_id`, `calculation_id`, `input_snapshot_id`, `retry_of`, `execution_group_id`, состояния |
| InputSnapshot | Геометрия, заряд/мультиплетность, метод/базис, растворитель, ограничения, фактические входные файлы и hashes |
| Batch | `batch_id`, назначение, упорядоченные ссылки на попытки и зависимости |
| ExecutionGroup | `group_id`, backend, server/cluster identity, `submission_token`, job ID, удалённая папка, члены группы |
| ResultRecord | `result_id`, `attempt_id`, версия парсера, научный исход, извлечённые свойства, ссылки на артефакты |
| Artifact | `artifact_id`, относительный путь, тип, размер, hash, состояние передачи и проверки |
| AnalysisTask | `analysis_id`, точные `result_id`/`artifact_id`, вид анализа, настройки, версия программы, состояние |

Одна молекула может иметь несколько планов: оптимизация, частоты, расчёт другим методом. Повтор создаёт новую Attempt, сохраняя Molecule и связь `retry_of`. Изменение метода или физической задачи по умолчанию создаёт другой CalculationPlan; изменение численных параметров для повторной попытки сохраняет семейство, но фиксируется в новом снимке.

`selected_result_id` задаёт результат, выбранный для просмотра. Для каждой серии можно отдельно хранить последний пригодный результат. Не использовать единое «последний результат молекулы» как неявную замену результата другого метода. Ошибка новой попытки не уничтожает прежний успешный результат. Сравнение энергий разрешается только при явно совместимых протоколах; несопоставимые значения не ранжируются автоматически.

После отправки снимок входных данных неизменяем. Предварительный поиск конформера – отдельный шаг подготовки: сохранить запрос пользователя и фактически выбранную для запуска структуру. Финальный InputSnapshot фиксируется после подготовки, до отправки. Последующая правка координат в Компасе создаёт новую рабочую ревизию и не изменяет снимок Attempt.

Для комплексов, ионов и BSSE сохранить роли и связи происхождения: `role`, `parent_molecule_id`, `fragment_ids`, `basis_context`. Служебные записи не должны самопроизвольно попадать в пользовательский пакет или QTAIM. Группы конформеров задаются явно, с проверкой связности, состава, заряда, спина и протокола сравнения; одинаковой формулы недостаточно.

## 5. Хранение и гарантии записи

**Рекомендуемое целевое решение: SQLite для метаданных и обычные файлы для расчётов.** При росте числа состояний, связей и восстановительных операций нужны транзакции сразу для нескольких записей. Это инженерный выбор для Azimuth, а не требование заменить формат до выделения ProjectSession. Первый этап может использовать существующий JSON через интерфейс Repository.

```text
Документы/Azimuth/Проекты/Лиганды/
  project.qcc                 # небольшой дескриптор формата и ID
  project.sqlite              # единственный источник метаданных
  inputs/<snapshot_id>/       # неизменяемые фактические входные файлы
  calculations/<attempt_id>/  # выводы, орбитали, геометрии и служебные файлы
  analyses/<analysis_id>/      # QTAIM и другие обработки
  imports/                    # копии исходных файлов и происхождение
  cache/                      # воспроизводимые поверхности/миниатюры
  exports/                    # пользовательские выгрузки
```

В новой схеме `project.qcc` не содержит второй изменяемой копии списка молекул и состояний. Старые `batch.json`, `job.json` и `project-link.json` после миграции – источники импорта либо совместимые производные представления с указанной ревизией; новые компоненты не читают их как конкурирующий источник истины. Список недавних проектов и locator `project_id → path` хранится в настройках приложения и восстанавливается из папок; он не заменяет данные самого проекта.

Для проекта допускается один процесс-писатель: межпроцессная блокировка, проверка владельца и явный режим чтения во втором окне. Внутри приложения команды проходят через последовательный обработчик; фоновые работники возвращают результаты, а не изменяют общие словари. Транзакция обновляет Attempt, связь ResultRecord и номер ревизии согласованно. Длительные SSH-операции и загрузка файлов выполняются вне транзакций. Событие UI публикуется после commit.

Файл и транзакция БД не образуют общую атомарную операцию. Артефакт сначала записывается во временный файл в том же файловом разделе, проверяется, закрывается и атомарно переименовывается; затем ссылка на него фиксируется в БД. Сбой между шагами оставляет обнаруживаемый незарегистрированный файл, а не ссылку на недописанный результат. Восстановление сверяет такие файлы по ID и hash. Для критических записей определить требования fsync и проверить поведение выбранных ОС/файловых систем.

Автосохранение рабочих правок отделить от явного пользовательского сохранения: хранить `working_revision` и `saved_revision`. После обычного ввода допустима небольшая задержка записи, например до 2 секунд; перед запуском, переключением проекта и закрытием – обязательная фиксация. Если запись не удалась, показывать несохранённое состояние и не запускать задание без устойчиво записанного намерения. Принудительное завершение процесса может потерять только ещё не зафиксированный интервал ввода, что нужно честно учитывать в тестах.

Активные проекты хранить на поддерживаемой локальной файловой системе. Синхронизация облаком не является блокировкой или резервным копированием работающей БД. При WAL нельзя копировать только основной файл базы; для согласованного снимка использовать SQLite Backup API или закрытие соединений по проверенному протоколу. WAL не рассчитан на сетевую файловую систему [S3, S4].

## 6. Состояния: выполнение, связь и доступность файлов

Не сводить все состояния к одному полю `status`. Отсутствие сети не означает ошибку вычисления; успешное завершение процесса не означает наличия файла волновой функции на компьютере.

| Измерение | Предлагаемые значения | Смысл |
|---|---|---|
| Submission | `prepared`, `submitting`, `accepted`, `uncertain`, `rejected` | Известно ли, что сервер принял отправку |
| Execution | `not_started`, `queued`, `running`, `succeeded`, `failed`, `cancelled`, `unknown` | Подтверждённое состояние выполнения |
| Connectivity | `online`, `offline`, `auth_required` | Доступность сервера и учётных данных |
| Artifacts | `not_requested`, `transferring`, `partial`, `ready`, `transfer_error` | Получение конкретного набора файлов |
| Scientific outcome | `unparsed`, `valid`, `unconverged`, `invalid`, `parse_error` | Пригодность результата для заявленной задачи |
| Cancellation | `none`, `requested`, `confirmed`, `failed` | Запрос отмены и подтверждение её выполнения |

Интерфейс строит короткую подпись из этих измерений: «Выполнялся; связь потеряна», «Расчёт завершён; загружаются орбитали», «Оптимизация не сошлась; последняя геометрия доступна». Показывать время последнего успешного наблюдения. Сведения из `squeue` описывают очередь, а `sacct` при доступной бухгалтерии SLURM предоставляет сведения о заданиях, шагах и кодах завершения [S1, S2]. Исчезновение задания из очереди само по себе не доказывает успех.

Каждое наблюдение содержит адрес Attempt/ExecutionGroup, источник, номер поколения наблюдателя и последовательность. После повторного подключения события старого наблюдателя отбрасываются. Позднее событие `running` не отменяет подтверждённый терминальный исход. Исправление противоречивых сведений – явная операция сверки с журналом причины. Для общей серверной группы итог отдельной молекулы определяется её записью завершения, а не только итогом SLURM allocation.

Успех процесса, сходимость оптимизации, пригодность для частотного анализа и наличие волновой функции проверяются раздельно. Несошедшаяся оптимизация может дать полезную геометрию или орбитали; они доступны с указанием происхождения и ограничения, но не обозначаются как успешная оптимизация.

## 7. Надёжный удалённый запуск

Порядок запуска обязателен. Кнопка «Рассчитать» сначала создаёт устойчивую запись, а затем вызывает внешний сервис. SLURM возвращает номер после приёма скрипта; это не означает, что расчёт уже начался [S1].

1. Проверить геометрию, заряд, мультиплетность, настройки и доступность необходимых программ. Создать Attempt и неизменяемые входные файлы. Для пакета заранее создать все попытки и членство ExecutionGroup.
2. В транзакции сохранить уникальный `submission_token`, намерение отправки и точный состав группы. Уникальность токена контролируется в хранилище. Повторное нажатие кнопки с тем же command ID возвращает уже созданную операцию.
3. Загрузить входные данные в каталог, адресованный `project_id/group_id`; проверить состав, размеры/hashes. Повтор загрузки безопасен, пока вычисление ещё не стартовало; файлы выполняющейся попытки не перезаписываются.
4. Серверный helper под блокировкой токена создаёт устойчивую запись намерения. Если уже существует квитанция приёма, возвращает прежний job ID. В `sbatch` передаётся идентификатор для поиска, например имя задания; сама строка имени не обеспечивает уникальности.
5. После приёма `sbatch` сохранить серверную квитанцию с токеном, job ID, идентичностью кластера, пользователем и папкой; затем сохранить локальную привязку одной транзакцией. Использовать машинно читаемый ответ, например `--parsable`, с учётом версии кластера [S1].
6. Только после подтверждения публиковать `accepted`; начать наблюдение. Ошибка локального сохранения после приёма сервером означает необходимость восстановления, а не разрешение повторно отправить расчёт.

**Не обещать exactly-once только наличием UUID.** Между приёмом задания планировщиком и сохранением квитанции остаётся окно сбоя. При потере ответа выставить `uncertain`, искать задание по токену, владельцу, папке, кластеру и ограниченному интервалу времени в доступных источниках. Одно найденное соответствие восстанавливает связь; несколько означают конфликт. Отсутствие записи в одном источнике не доказывает отсутствия задания. При неустранимой неоднозначности автоматическая отправка блокируется; пользователю показываются сведения для проверки. Явный повтор оформляется новой попыткой с зафиксированным решением.

Операции `submit_new` и `resume_watch` должны иметь разные публичные интерфейсы. Восстановление никогда не вызывает `submit_new` для уже отправленной или неоднозначной попытки. Серверный helper и клиент обязаны проверяться с искусственным обрывом связи после фактического приёма задания.

## 8. Пакеты и серверные группы выполнения

Batch – логическая выборка попыток. ExecutionGroup – способ их выполнения. Возможны одна молекула в одном SLURM job, много молекул в одном последовательном скрипте и, позднее, job array. Одна Attempt принадлежит не более одной активной группе. Повтор проблемной молекулы создаёт новую Attempt и новую связь, а не заменяет элемент старой группы.

Сохранить нынешнюю возможность Azimuth отправлять весь пакет одним архивом и выполнять его без работающего клиента. Последовательность молекул на сервере продолжает выполняться после закрытия настольной программы. Если режим подготовки конформеров требует локального клиента, перед отправкой подготовить все исходные файлы либо явно обозначить эту зависимость; нельзя обещать автономность очереди, которая ждёт следующего шага от окна.

Для группы сервер хранит неизменяемый manifest: упорядоченные attempt IDs, пути и hashes входов. Для каждого элемента – атомарные записи старта и завершения с attempt ID, кодом выхода и подтверждёнными выходными файлами. Состояния отдельного элемента могут быть `not_started`, `running`, `succeeded`, `failed`, `cancelled`; непрочитанный статус не подменять успехом. Прерванный скрипт группы оставляет ещё не начатые элементы отличимыми от упавшей молекулы.

Остановка строки и остановка пакета – разные команды. В общем SLURM job команда остановки строки не должна выполнять `scancel` общего номера. Серверный runner поддерживает пропуск ожидающей строки и управляемое прекращение активного дочернего процесса с переходом к следующему. Если backend не умеет это надёжно, соответствующая команда недоступна с объяснением; запуск отдельного расчёта предоставляет альтернативу. Отмена группы использует её job ID и подтверждается наблюдением.

Прогресс пакета вычисляется из сохранённых состояний элементов. Начальный состав Batch фиксирован; добавление молекул в проект не меняет уже отправленную группу. Для новых молекул создаётся новый пакет/группа. Назначение Batch обязательно: `structures`, `conformers`, `binding`, `fukui`, `cda` или `analysis`. Научные зависимости описываются явно; состав группы SLURM не определяет смысл молекул.

## 9. Восстановление после повторного запуска

Восстанавливаются данные и привязки, а Python-объекты наблюдателей создаются заново. Текущая вкладка, `queue.document` и указатель на окно не являются данными восстановления.

1. Прочитать локальный реестр проектов, доступные дескрипторы и метаданные. Показать сохранённые проекты, молекулы и последние известные состояния до обращения к сети.
2. Получить блокировку писателя и восстановить незавершённые локальные записи артефактов/миграций. При недоступной папке сохранить запись в реестре и предложить указать её новое место.
3. Найти группы `accepted`, `uncertain` и незавершённые Attempt. Сгруппировать наблюдение по серверу и group ID: 44 молекулы одного job не требуют 44 независимых запросов SLURM.
4. Проверить профиль подключения. Секреты находятся в системном хранилище; проект содержит только ссылку и идентичность сервера. При другом компьютере запросить привязку профиля. Переименование профиля не меняет принадлежность задания к кластеру.
5. Сверить серверную квитанцию, SLURM и записи элементов группы. Недоступность сети оставляет последние сведения с отметкой об их давности. Повторы соединения имеют задержку и верхний предел частоты; они не являются повторными отправками.
6. Для завершённых элементов загрузить недостающие файлы, разобрать результат и восстановить доступные действия. Повторное открытие того же проекта или повторная доставка события не создаёт второго результата.
7. Восстановить вкладки, выбранную молекулу и раздел из WorkspaceState. Явное действие «Открыть очередь» открывает её проект; обычное фоновое обновление не переводит пользователя на него.

Если работа закрытого проекта продолжается, RunCoordinator удерживает доступ к его Repository независимо от ProjectView. При завершении всего приложения удалённые задания продолжаются на сервере, наблюдение прекращается. Незавершённая локальная очередь не объявляется автономной: если её продолжение зависит от процесса Azimuth, это явно показывается перед выходом. При повторном подключении к локальному процессу одного PID недостаточно: проверяются время запуска и идентификатор попытки; иначе состояние требует уточнения.

## 10. Результаты, плотность и QTAIM до конца пакета

Готовность определяется для каждой Attempt и каждого свойства. Не вводить условие «весь Batch завершён» для доступа к результату отдельной молекулы.

| Возможность | Минимальное основание для доступности |
|---|---|
| Энергия и геометрия | Проверенные фрагменты вывода и успешный разбор соответствующих величин |
| Колебания/спектры | Соответствующие данные задачи, единицы и признаки пригодности |
| Орбитали/плотность | Поддерживаемый проверенный файл волновой функции либо подходящая сетка; необходимые преобразования завершены |
| QTAIM | Файлы, достаточные выбранному анализатору, доступная программа, проверенные настройки |
| Сравнение нескольких молекул | Явная выборка результатов и проверка совместимости сравниваемых величин |

Пример: из 44 молекул пять завершены. У третьей получены файлы для плотности – пользователь открывает её в Спектре и запускает QTAIM. Четвёртая ещё загружает орбитали – доступны энергия/геометрия и подпись «Загрузка файлов для плотности». Оставшиеся вычисляются. Завершение шестой обновляет её строку и счётчики; третья остаётся выбранной.

AnalysisTask ссылается на конкретный ResultRecord, hashes входных артефактов, настройки и версию анализатора. Повтор расчёта молекулы не переназначает уже запущенный QTAIM на новые файлы. Новый результат получает новую задачу анализа. Ключ повторного использования анализа включает научные входы и настройки; одинакового имени молекулы недостаточно.

Предусмотреть два явных действия: «Анализировать готовые выбранные» фиксирует набор result IDs сейчас; «Анализировать выбранные по мере готовности» создаёт сохранённые зависимости на конкретные attempt IDs. Второе не запускается просто при открытии проекта: это заранее данная команда пользователя. Ошибка расчёта переводит зависимый анализ в понятное состояние ожидания/невыполнимости; автоматическое использование результата другого метода запрещено.

У AnalysisCoordinator отдельная очередь и лимиты ресурсов. Он может работать параллельно с удалённой вычислительной очередью. Две локальные тяжёлые задачи учитывают общий бюджет CPU/RAM; удалённый анализ учитывает ограничения сервера. Ошибка анализа не переводит успешный квантово-химический расчёт в failed. Конвертация волновой функции и формирование CUBE – самостоятельные восстанавливаемые шаги; их ошибка не уничтожает исходные файлы.

## 11. Контракты UI, перенос и совместимость

Ниже предлагаемые интерфейсы, а не готовые имена существующих функций. Их смысл должен сохраняться при изменении реализации.

```python
session.open_or_create(source, mode='new_project')
session.add_molecules(records, expected_project_revision)
session.edit_molecule(molecule_id, patch, expected_molecule_revision)
session.get_export_snapshot(molecule_ids) -> immutable_snapshot
session.prepare_run(molecule_ids, settings) -> RunPlan
runs.submit_new(run_plan_id, command_id) -> execution_group_id
runs.resume_watch(execution_group_id) -> WatchHandle
runs.cancel_attempt(attempt_id, command_id)
results.list_capabilities(result_id) -> capabilities_with_reasons
analyses.enqueue(result_ids, settings, command_id) -> analysis_ids
session.save(expected_project_revision)
```

Команды имеют устойчивые ID для повторной доставки, ожидаемую ревизию для изменений и структурированную ошибку. Событие включает `project_id`, `entity_id`, `project_revision`, `event_id`. UI отбрасывает старые события и применяет новые к правильной модели, даже если её вкладка закрыта. Научное изменение и выбор вкладки – разные события. Сетевые callbacks не читают `current_document` для определения адресата результата.

Переименование меняет display name, сохраняя ID. Перенос сохраняет ID, копирование создаёт новый project ID. В первой реализации физический перенос/копирование проекта с активной отправкой, загрузкой, анализом или вычислением блокируется с понятной причиной; обычное сохранение и переименование доступны, потому что проект с самого начала находится в постоянной папке. Позднее перенос можно поддержать через отдельный журнал операции и переключение locator после полной проверки, без остановки удалённого расчёта.

Копирование завершённого проекта сохраняет происхождение результатов и относительные пути, но копия не принимает управление старыми серверными заданиями. Совпадение project ID в двух разных папках нельзя молча считать одним открытым проектом: показать конфликт и предложить открыть оригинал либо зарегистрировать независимую копию. Резервная копия отличается от пользовательского клона: она сохраняет идентичность для восстановления, но не открывается как второй писатель.

Миграция JSON → SQLite выполняется только для остановленного с точки зрения изменений проекта: незавершённые удалённые задания сначала обслуживаются старым адаптером. Создать резервную копию; импортировать записи и относительные пути в новую БД; проверить количество молекул/попыток, ID, ссылки и hashes входов; затем атомарно переключить дескриптор формата. Исходные файлы оставить для восстановления. Повтор миграции безопасен. Старые версии программы должны явно отвергать новый формат, а не перезаписывать его как старый JSON.

Старые ID попыток сохраняются. Недостающий submission token импортированного задания не выдумывается как доказательство отправки: восстановление использует существующий job ID, сервер и папку, отмечая ограничения проверки. Поле `current` старой модели импортируется как явный выбор результата с прежним происхождением.

## 12. Поэтапная реализация

Каждый этап – самостоятельное изменение с тестами и возможностью остановиться на рабочей версии. Точный номер выпуска назначается в roadmap при принятии этапа в разработку.

| Этап | Результат | Условие завершения |
|---|---|---|
| A. Контракты и сценарии | Владельцы данных, состояния, фиксированные сценарии ошибок | Разработчик может объяснить адресата каждого события без обращения к текущему окну |
| B. ProjectSession поверх JSON | Единые чтение актуальной структуры, экспорт, сохранение и жизненный цикл вкладки | Редактирование/экспорт/закрытие проходят через Session; старые проекты читаются |
| C. RunCoordinator | Одна молекула: отправка, закрытие приложения, восстановление и результат | Результат приходит в исходную попытку; потеря ответа не вызывает дубль |
| D. ExecutionGroup | Несколько попыток в общем SLURM job и автономная очередь | Закрытие клиента не останавливает оставшиеся элементы; отмена строки не отменяет группу |
| E. AnalysisCoordinator | Анализ отдельного готового результата и сохранённые зависимости | QTAIM одной молекулы работает при продолжающемся пакете |
| F. Транзакционное хранилище | SQLite Repository, миграция, резервирование | Нет двух источников метаданных; прерывание миграции восстанавливается |
| G. Удаление старых связей | UI использует команды и снимки, обновлена документация | Научная логика проекта тестируется без Qt; дублирующие поля/ветви удалены |

Начать с вертикального сценария одной молекулы, затем расширять до пакета. Не начинать с массового переименования классов. Адаптер JSON на этапах B–E должен обеспечить те же гарантии фиксации намерения и согласованного изменения метаданных, например одной атомарной записью общего manifest; независимые несогласованные записи нескольких JSON не считаются эквивалентом транзакции.

Первый рабочий результат для демонстрации: открыть молекулу → автоматически получить проект → отправить расчёт → закрыть Azimuth → открыть снова → восстановить наблюдение → открыть результат той же попытки. Следующий: добавить вторую молекулу и во время её расчёта анализировать первую.

## 13. Приёмочные проверки

Проверять поведение через публичные команды и сохранённые результаты. Имитации допустимы на границе SSH/SLURM, запуска внешней программы и часов; внутренние компоненты должны взаимодействовать реально. Отдельно выполнять согласованный небольшой сценарий на настоящем сервере. Запуск тестов и отправка научных задач – разные действия.

| № | Сценарий | Ожидаемый результат |
|---|---|---|
| T01 | Открыть один XYZ или SDF с 44 структурами | Один новый проект; правильное имя, порядок и постоянные ID |
| T02 | Добавить структуры в текущую вкладку | Существующие молекулы и история сохраняются; новая вкладка не возникает |
| T03 | Нарисовать первую молекулу, закрыть приложение | Черновик найден в папке проектов; восстановлены последние зафиксированные правки |
| T04 | Изменить координаты и сразу экспортировать/запустить | Использована актуальная ревизия, без включения молекул другого проекта |
| T05 | Выполнять А, редактировать Б, дождаться А | Обновляется попытка А; структура, выбор и анализ Б сохранены |
| T06 | Сбой до отправки, после сохранения намерения | Восстановлена prepared; отправка требует команды, дубля нет |
| T07 | Сервер принял job, ответ потерян | uncertain; сверка восстанавливает единственную связь либо останавливается для уточнения |
| T08 | Сервер принял job, диск клиента заполнен | Нет автоматической повторной отправки; сведения о принятом задании доступны для восстановления |
| T09 | Сервер недоступен при запуске приложения | Проект открывается локально; последнее состояние и давность видны |
| T10 | Job исчез из squeue, вывод/учёт задерживаются | Нет ложного успеха; сверка ждёт достаточных доказательств |
| T11 | Дважды доставить событие завершения | Одна запись результата, без повторного автоматического анализа |
| T12 | Перезапустить клиента во время общего SLURM job | Очередь продолжает выполняться; элементы восстановлены по собственным ID |
| T13 | Остановить одну строку общего job | Остальные продолжаются либо UI заранее сообщает, что backend не поддерживает эту операцию |
| T14 | Повторить пять ошибочных из 44 | Новые попытки у тех же пяти молекул; исходная история не изменена |
| T15 | Загрузить орбитали одной готовой молекулы | Плотность/QTAIM доступны до окончания остальных 43 |
| T16 | Оборвать передачу большого файла | Неполный файл не объявлен готовым; передача восстанавливается с проверкой |
| T17 | Ошибка конвертации или Multiwfn | Расчёт остаётся успешным; ошибка относится к отдельной обработке |
| T18 | Пересчитать молекулу во время её QTAIM | Анализ завершён для первоначально выбранных result/artifact IDs |
| T19 | Открыть один проект во втором процессе | Второй писатель не создаётся; исходное задание не отправляется повторно |
| T20 | Сбой во время сохранения/миграции | Старое или новое согласованное состояние; нет смешанной схемы |
| T21 | Перенести завершённый проект; открыть копию | Пути работают; перенос сохраняет ID, независимая копия получает новый ID |
| T22 | Одинаковые формулы у разных веществ | Пакет не превращается автоматически в ансамбль конформеров |
| T23 | Смена метода/заряда/геометрии | Результаты и анализ не перепривязаны; несовместимость ясно обозначена |
| T24 | Сквозной пакет на настоящем сервере | Открытие → расчёт → перезапуск → повтор ошибок → QTAIM → сохранение → повторное открытие |

Инъекции сбоев ставятся до и после каждой границы фиксации: запись входа, commit намерения, передача, приём sbatch, сохранение квитанции, локальная привязка, переименование артефакта, регистрация результата. Для T07 нужны также ноль и несколько найденных кандидатов. Для T24 достаточно небольшого безопасного пакета с заранее согласованными ресурсами; проверку на 44 молекулах выполнить отдельно на рабочем наборе владельца.

## 14. Что разработчик должен передать

Реализация считается готовой после передачи: схемы владения данными; описания состояний и переходов; публичных контрактов команд/событий; версии схемы и проверенной миграции; тестов T01–T24 с указанием выполненных и невыполненных; журнала реального восстановления удалённого задания; обновлённого roadmap и инструкции пользователя.

В отчёте перечислить backend-возможности конкретного кластера: доступность accounting, сроки хранения записей, способы поиска submission token, поддержку отмены элемента общего job, доступность удалённой конвертации орбиталей. Не подменять эти проверки предположением о стандартной конфигурации SLURM. Поддержка Windows/macOS подтверждается отдельно.

Перед реализацией согласовать только оставшиеся продуктовые параметры: задержку автосохранения, пределы одновременных анализов и политику автоматической загрузки крупных файлов. Основные решения уже заданы этим руководством: автоматические проекты, папка проектов, независимые результаты молекул и восстановление без повторной отправки.

## 15. Источники и навигация по коду

Это руководство содержит инженерные рекомендации для Azimuth. Документация ниже подтверждает свойства внешних инструментов; она не доказывает, что целевая архитектура уже реализована.

- [S1] SchedMD, sbatch: приём задания, job ID и машинно читаемый ответ. https://slurm.schedmd.com/sbatch.html
- [S2] SchedMD, sacct: учёт заданий и шагов, состояния и коды завершения; доступность зависит от конфигурации. https://slurm.schedmd.com/sacct.html
- [S3] SQLite, Backup API: согласованное копирование работающей базы. https://www.sqlite.org/backup.html
- [S4] SQLite, WAL: ограничения сетевых файловых систем и правила работы с WAL. https://www.sqlite.org/wal.html

Проверенные точки входа текущей версии, пути относительно папки программы:

- `azimuth/projects.py`: `Project`, `edit`, `attach`, `sync`, `queueable` – сохранение и связь с очередью.
- `azimuth/project_actions.py`, `azimuth/project_navigation.py` – управление проектами и переходы UI.
- `modules/compass/panels/documents.py` – внутреннее состояние документов молекул.
- `modules/sextant/remote_job.py`: `RemoteJob`, `BatchItemJob`, `submit`, `send_batch` – удалённое выполнение.
- `modules/sextant/batch.py`, `batch_retry.py`, `batch_actions.py` – пакет, повтор и взаимодействие с окном.
- `modules/spectrum/wavefunction/batch_qtaim.py` – пакетный анализ результатов.
- `azimuth/recovery.py`, `recovery_ui.py`, `tasks.py` – восстановление и фоновая работа.
- `docs/plans/ROADMAP.md`, `docs/ARCHITECTURE.md`, `docs/audits/AUDIT.md` – план и существующие архитектурные записи. Устаревшие сведения сверять с кодом указанной версии.
