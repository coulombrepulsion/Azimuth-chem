# Контракты проектов и расчётов

Начато в 0.107.0 (этап A), дополнялось по этапам B–G; сверено с кодом 0.108.74. Этап A из [PROJECT_RUNTIME_GUIDE.md](PROJECT_RUNTIME_GUIDE.md) (§12). Здесь закреплены владельцы данных, состояния попытки, адресация событий и команд и статус приёмочных сценариев. Код контрактов — `azimuth/runtime/` (чистый Python, без Qt). Тесты — `tests/runtime/`.

Условие завершения этапа A: разработчик может объяснить адресата каждого события, не обращаясь к текущему окну. Для нынешнего кода это делает раздел 4, для будущего — разделы 2 и 3.

## 1. Владельцы данных

`azimuth/runtime/contracts.py`, `OWNERS`:

| Данные | Владелец | Что видит интерфейс |
|---|---|---|
| Список молекул, порядок, названия | ProjectSession / ProjectRepository | Снимок списка и ID выбранной молекулы |
| Несохранённые координаты и настройки | WorkingMolecule в ProjectSession | Редактируемая проекция с номером ревизии |
| Исходные данные отправленной попытки | InputSnapshot (неизменяемый) | Просмотр входа попытки |
| Состояние удалённого выполнения | RunCoordinator, хранит ProjectRepository | Последнее подтверждённое состояние и его давность |
| Файлы и результаты | ArtifactStore / ResultRecord | Доступные свойства и причина недоступности остальных |
| Камера, раскрытые панели, прокрутка | WorkspaceState | Только представление, не источник научных данных |

До этапов B–G этими данными владели `project.qcc` (через `azimuth/projects.py`), документы молекул (`modules/compass/panels/documents.py`), окно `Studio` и `batch.json` / `job.json` / `project-link.json`. Сейчас (0.108): список молекул, их структуры и настройки, попытки, записи расчётов и очередей — в `project.sqlite` (`projects.py`, `runtime/records.py`), рабочие правки — в ProjectSession (`runtime/session.py`); `project.qcc` — указатель, `batch.json` — производный файл. Вид вкладки — Undo, закреплённые измерения, векторы и плоскости, ящик результата и выбранные в нём шаг и конформер — с 0.108.65 отдельная запись `azimuth/runtime/workspace_state.WorkspaceState` (`document.view`; прежние имена полей документа — свойства, которые читают и пишут её); хранилище, слой выполнения, копии восстановления и входные файлы её не читают (`tests/core/test_architecture_boundaries.py::test_the_view_of_a_tab_is_never_data`).

## 2. Состояния попытки

`azimuth/runtime/states.py`. Шесть независимых измерений; разрешённые переходы перечислены в `TRANSITIONS`.

| Измерение | Состояния | Особые правила |
|---|---|---|
| submission | prepared → submitting → accepted / rejected / uncertain | `uncertain` меняется только сверкой (`reconcile`) с указанием причины и никогда не разрешает отправить заново |
| execution | not_started, queued, running, succeeded, failed, cancelled, unknown | Терминальные (succeeded, failed, cancelled) меняет только `reconcile`. running → queued допустим: SLURM ставит задание в очередь повторно |
| connectivity | online, offline, auth_required | Не влияет на execution: нет сети — не ошибка расчёта |
| artifacts | not_requested → transferring → partial / ready / transfer_error | ready → transferring — запрошен другой набор файлов, например орбитали после энергии |
| outcome | unparsed → valid / unconverged / invalid / parse_error | Обратно в unparsed — перечитать новым парсером |
| cancellation | none → requested → confirmed / failed | Отмена строки и отмена группы — разные команды (этап D) |

Наблюдения (`Observation`) несут поколение наблюдателя и порядковый номер. `accept()` отбрасывает:
- наблюдение старого поколения — `stale`, наблюдатель заменён после переподключения;
- повтор — `duplicate`;
- нетерминальное наблюдение после терминального состояния — `late`, поздний `running`.

Другой терминальный исход после терминального — `conflict`. Он не применяется, решение принимает `reconcile`.

`caption()` строит короткую подпись интерфейса: «Выполнялся; связь потеряна», «Расчёт завершён; загружаются файлы», «Расчёт завершён; без сходимости; последняя геометрия доступна».

## 3. Команды и события

`azimuth/runtime/contracts.py`:
- **Идентификаторы.** `new_id()` — 32 шестнадцатеричных знака. Создаются до любого внешнего действия: отправки, записи файла.
- **Command.** Содержит `name`, `command_id`, `expected_revision` и `arguments`. Повторная доставка того же `command_id` — та же операция. Изменение против старой ревизии отклоняется с `CommandError('stale_revision')`.
- **Event.** Содержит `project_id`, `entity_id`, `project_revision`, `kind`, `payload` и `event_id`. Публикуется после записи изменения.
- **Delivery.** Принимающая сторона применяет событие один раз (T11) и не применяет событие более старой ревизии проекта. Получатель — модель проекта, а не окно: событие применяется и к проекту, вкладка которого закрыта.

## 3a. Открытый проект — ProjectSession (этап B, с 0.107.1)

`azimuth/runtime/session.py`. На каждый `project_id` приходится одна сессия (`SessionRegistry`): тот же путь — та же сессия. Тот же ID из другой папки — `ProjectConflict`: копия обязана получить свой ID.

Сессия — единственный владелец рабочего состояния молекул проекта: координат, настроек, программы, формальных зарядов и признака «плоская». Редакторы передают ей свои правки через `edit_molecule`. Команды читают из неё: `structure`, `snapshot`, `export_snapshot`. `save()` записывает только изменённые молекулы через `projects.edit`, поэтому попытки, записанные очередью тем временем, сохраняются. Номер ревизии проекта хранится в `project.qcc` (`revision`) и растёт при каждой записи сессии. У молекулы есть `working_revision` и `saved_revision`.

Через сессию сейчас идут:
- сохранение проекта (`save_research_project`);
- добавление молекулы вкладки (`add_current_to_project`);
- добавление молекул из файлов (`import_project_structures`);
- экспорт «Сохранить все структуры» (`batch_structures`);
- закрытие вкладки (`close_project_tab`).

«Сделать 3D» по-прежнему пишет в файл напрямую, а затем сбрасывает рабочие правки этих молекул в сессии.

Имя проекта: проект, открытый из одного файла, называется по файлу. Если к проекту из одной молекулы добавляют молекулы, а имя пользователь не выбирал, проект становится «Новый проект». Имя, данное при первом сохранении, хранится с отметкой `named` и не меняется.

Документы Компаса пока остаются редактором: они держат модель на экране, Undo, шторку и результат. Сессия получает их состояние перед каждой командой (`push_project_documents`).

С 0.107.2 черновик сразу получает постоянную папку `~/Documents/Azimuth/Проекты/<название>` (`azimuth/project_folders.py`; на Windows — латиницей, корень выбирается в настройках). «Сохранить» подтверждает название, ничего не копируя; «Перенести проект» (`move_project_tab`) переносит папку целиком с тем же ID и запрещён во время расчёта.

С 0.107.3 строки очереди проекта (`project_batch_rows`) читаются из сессии (`queue_view` — рабочее состояние, несохранённые правки тоже; ключ кэша включает `working_key`), а молекула, открытая в новой вкладке (`open_project_molecule`), берётся из `session.structure`, а не из сохранённого JSON.

Этап B закрыт на уровне адаптера: документы Компаса остаются редактором и передают состояние сессии перед командами (`push_project_documents`). Полный перенос Undo и состояния отображения в WorkspaceState — этап G.

## 3b. Отправка одного расчёта — этап C (с 0.107.4)

`azimuth/runtime/runs.py`, `modules/sextant/remote_job.py`. Порядок §7 руководства:

1. `prepare_remote` пишет в папку расчёта входные файлы, `job.sh`, помощник `az-submit.sh` и `submission.json` в состоянии `prepared` (attempt ID, токен, имя задания). Это намерение — до обращения к серверу (T06: после перезапуска история показывает «подготовлен, не отправлен», ничего не отправляется само).
2. Попытка записывается в проект (`register_project_job`, тот же attempt ID) и историю до старта отправки.
3. Загрузка папки (повторяется при обрыве), затем запись `submitting` и вызов помощника.
4. Помощник на сервере под блокировкой токена (`mkdir .az-lock`) вызывает `sbatch --parsable -J <имя>` один раз и пишет квитанцию `.az-receipt`. Повторный вызов с тем же токеном отдаёт прежнюю квитанцию.
5. Ответ получен → `accepted` (номер), `job.json`, наблюдение. Отказ → `rejected`.
6. Ответ потерян → сверка (`find_command`, `verdict`): квитанция → `accepted`; нет блокировки → помощник не запускался, вызывается снова с тем же токеном (это та же отправка); блокировка без квитанции → задания пользователя с именем токена в `squeue` и `sacct`: одно → `accepted`, несколько → конфликт, ни одного → `uncertain`. Сервер недоступен → `uncertain`.
7. `uncertain` меняется только `settle()` с причиной в журнале записи — по «Проверить на сервере» (`RemoteJob.resume` без номера → `_settle`). Повторная отправка — только новым расчётом, новой попыткой с новым токеном.

`submit_new` и `resume_watch` разделены: `RemoteJob.start()` у новой папки отправляет, `RemoteJob.resume(...)` никогда не вызывает отправку — только сверку или наблюдение.

Пока не сделано в этапе C: результат в окне по-прежнему находит вкладку через `job_document` (запись в проект уже идёт по attempt ID — T05 partial); очередь серверу отправляется одним скриптом без токена (этап D, ExecutionGroup). Открытый вопрос к владельцу (§14 руководства): есть ли `sacct` на serv2–serv4 и как долго он хранит записи.

## 3c. Очередь одним заданием — ExecutionGroup (этап D, с 0.107.5)

`remote_job.send_batch`, `BatchItemJob`, `cluster.batch_script`, `runs.write_group`.

- В папке скрипта очереди (`<очередь>-batch`) до отправки пишутся `group.json` — неизменяемый состав группы: ID группы, по порядку скрипта attempt ID, папка, основа имени и SHA-256 входного файла каждого элемента — и запись отправки группы (`submission.json`, свой токен). Повторная запись состава запрещена.
- Скрипт ставится через тот же помощник, что и одиночный расчёт (этап C): один `sbatch` на токен, квитанция на сервере. Архив и постановка — по-прежнему одним обращением `ssh`.
- Метки элемента: `.az-started` — «время attempt», `.az-finished` — «код attempt», каждая пишется во временный файл и переносится. `BatchItemJob` принимает только метку своей попытки: метка другой попытки не считается его завершением.
- Потерянный ответ при постановке очереди — сверка с сервером. Не решено → `SubmissionUncertain`: `job.json` элементов без номера, с `group` — локальной папкой группы. Очередь не отправляется повторно и не уходит «по одному» (так было до 0.107.5 при любой ошибке). Наблюдение первого элемента сверяет группу и записывает её номер; остальные берут его из записи группы без обращения к серверу.
- Повтор той же очереди из той же папки с тем же составом идёт по тому же токену и дубля не даёт; с другим составом — отказ, нужна новая очередь.
- Остановка строки — метка `.az-skip`, остановка очереди — `scancel` общего номера (как с 0.106.6, T13).

С 0.108.30 элемент очереди, оставшийся `uncertain`, так и остаётся `uncertain` (`lifecycle.row_state`), а не «ошибка»: повтор для него не готовится (`batch.NOT_REPEATABLE`, `batch_retry.prepare`), в обозревателе пакетов — «Проверить на сервере» (`check_uncertain_item`: строка снова наблюдается, сервер спрашивают по той же метке, ничего не отправляется). Очередь при этом не ждёт его бесконечно (`Batch.done`). Наблюдение по-прежнему идёт по элементам, а не одним запросом на группу (§9 руководства, п. 3).

## 3d. Анализ отдельно от расчёта — этап E (с 0.107.6)

`azimuth/runtime/analysis.py`, `modules/spectrum/wavefunction/batch_qtaim.analyse`.

- Перед каждым анализом файл орбиталей копируется (`snapshot`: то же имя, SHA-256, размер) во временную папку `Анализ/.az-input-<k>`; Multiwfn и чтение орбиталей идут по копии. Расчёт, повторённый тем временем, анализ не меняет (T18). Таблицы пишутся, как раньше, рядом с исходным файлом.
- Каждый анализ — запись в журнале `Анализ/analyses.json` папки очереди: ID анализа, вид (`qtaim`), attempt ID (из записи отправки, для локального расчёта — `folder:<папка>`), имя и SHA-256 артефакта, состояние `running → succeeded | failed`, ошибка, время. Запись атомарная.
- Ошибка Multiwfn или чтения — состояние анализа, а не расчёта: строка очереди остаётся «готово» (T17).
- Анализ берёт готовые строки, не дожидаясь остальных (T15) — так было и раньше («QTAIM для всех» доступна с первой готовой).

Пока не сделано: анализ запускается командой пользователя и идёт в том же потоке ожидания, что и раньше; автоматического планирования после каждой готовой строки и отдельной очереди анализов (AnalysisCoordinator как служба) нет — это следующий шаг, если владелец его захочет. Повтор анализа по команде делает новую запись, старая остаётся.

## 3e. Один писатель проекта, копия и сбой записи — этап F, первая часть (с 0.107.7)

`azimuth/runtime/writer_lock.py`, `projects.edit`, `projects.copy_project`, `SessionRegistry`.

- Писатель проекта держит блокировку операционной системы на `.az-writer.lock` в папке проекта (`fcntl.flock` на macOS и Linux, `msvcrt.locking` на Windows), пока проект открыт; `.az-writer.json` рядом говорит, кто держит (узел, процесс, с какого времени). Система снимает блокировку, когда процесс завершается, даже аварийно — «зависшей» блокировки не бывает. Внутри процесса блокировка считается по числу открытий.
- `SessionRegistry.open` берёт блокировку; держит другой процесс → `session.read_only` (кто), окно говорит один раз «только просмотр». `projects.edit` в таком процессе отказывает (`ProjectLocked`) — это закрывает и запись попыток, и сохранение, и импорт (T19). `close` отпускает блокировку; «Перенести проект» закрывает сессию до переноса.
- «Сохранить как…» проекта — `copy_project`: вся папка без файлов блокировки, новый ID, `copied_from` — ID оригинала; ID молекул и попыток сохраняются (история). Перенос сохраняет ID (T21).
- Запись `project.qcc` — временный файл и `os.replace`: сбой на замене оставляет прежний файл целым и не оставляет временного (T20, часть про сохранение).

Предположение: папка проекта на локальном диске; на сетевом или облачном диске блокировка может ничего не блокировать.

## 3f. Метаданные проекта в SQLite — этап F (с 0.108.0, решение владельца от 2026-11-09)

`azimuth/project_store.py`, `projects.Project.load/save/view`, `projects.stamp`, `projects.copy_project`.

- `project.qcc` — короткий дескриптор `{format, version: 2, database: "project.sqlite"}`. Метаданные — в `project.sqlite`: `meta` (`schema`, `generation`, `document` — поля проекта, кроме молекул), `molecules` (запись молекулы без попыток, порядок), `attempts` (попытки молекулы, порядок). Файлы расчётов остаются файлами.
- Запись — одна транзакция `BEGIN IMMEDIATE … COMMIT`; читатель видит прежний или новый проект; сбой внутри — откат (T20). `journal_mode=DELETE`, `synchronous=FULL`, ожидание занятости 10 с. WAL не используется: папку проекта переносят и копируют.
- Кэш `Project.view` и строки очереди проекта сверяются с `generation` базы (растёт при каждой записи), а не со временем файла.
- Миграция проекта версии 1 — при его первой записи (чтение ничего не меняет): база целиком в `project.sqlite.migrating` → перенос на `project.sqlite` → прежний JSON сохраняется как `project.qcc.v1-backup` → `project.qcc` атомарно заменяется дескриптором. До последнего шага в силе прежний `project.qcc`, оставшаяся база перезаписывается при следующей записи; после — новый проект (T20, сбой на каждом шаге).
- Схема новее известной — проект не читается и не перезаписывается. Повреждённая база — понятная ошибка.
- «Сохранить как…» копирует базу через SQLite Backup API.
- Азимут до 0.108 на дескрипторе отвечает «Неизвестный формат проекта с расчётами» и ничего не пишет: проект, сохранённый 0.108, открывается только 0.108 и новее.

Что остаётся вне базы: `batch.json` очередей, `job.json`, `submission.json`, `group.json`, `analyses.json` и `project-link.json` — записи рядом с файлами расчётов, у каждой свой атомарный файл. Перенос их в базу — этап G.

## 3g. Записи расчётов проекта — этап G, первая часть (с 0.108.1)

`azimuth/runtime/records.py`. Папка расчёта внутри проекта версии 2 (ближайший родитель с `project.qcc`-дескриптором) хранит свои записи — `submission.json`, `job.json`, `group.json`, `project-link.json`, `analyses.json` — строками таблицы `records` в `project.sqlite`: ключ — папка относительно проекта и имя. Запись — одна транзакция, файл того же имени после неё удаляется, поэтому источник один. Файл без строки читается как есть (импорт) и переходит в базу при следующей записи. Вне проекта и в проекте версии 1 — файлы. При втором процессе-писателе запись отклоняется (`ProjectLocked`).

С 0.108.3 и очередь проекта — строка базы (`records`, имя `batch.json`); файл `batch.json` пишется после неё как производное представление (§5 руководства): по нему список «Очереди» и «Открыть…» находят очередь на диске, а `Batch.load` читает строку. Устаревший файл (сбой после записи строки) не читается раньше строки.

С 0.108.2 результат одиночного расчёта идёт во вкладку по ID попытки (`azimuth/runtime/delivery.py`, `run_actions.result_tab_of`): для расчёта проекта — вкладка молекулы попытки, какой бы вкладка ни была сейчас; закрытая — открывается снова, если её проект активен, иначе результат в новой вкладке. Вне проекта — вкладка запуска, пока она открыта. `job_document` остался только запасным адресом расчёта вне проекта. С 0.108.3 и результаты очереди конформеров («Конформеры» вкладки) находят вкладку по ID молекулы, сохранённым в `batch.json` (`extra.origin`), — после перезапуска тоже; `queue.document` — запасной адрес вне проекта (`tab_for`).

С 0.108.4 «записи нет» — только ответ исправной базы (или базы 0.108.0 без таблицы `records`); повреждённая, отсутствующая или занятая база — `ProjectDatabaseError`, файл рядом не читается вместо неё.

Этап G закрыт для данных и адресатов событий: метаданные проекта, записи расчётов и очередей — в `project.sqlite`, результаты находят вкладку по ID. Осталось вне этапа (по мере надобности): вид вкладки — отдельная запись WorkspaceState с 0.108.65, наблюдение очереди идёт по элементам, а не одним запросом на группу; T24 — ручная проверка на настоящем сервере с владельцем.

## 3h. Одиночный расчёт без окна — шаг B обзора 2026-11-09 (с 0.108.32)

`azimuth/runtime/single_run.py`: снимок входа → запуск → наблюдение → итог → записи → что показать. Окно только показывает итог и предлагает разрешённые им действия.

1. Вход попытки — её собственный снимок: `lifecycle.Attempt` копирует `input` и `extra` при создании (frozen-dataclass не замораживает вложенный словарь).
2. `SingleRun.start` — строка истории и попытка `running` в проекте (`Lifecycle.started`).
3. `SingleRun.observe(job)` — `running` / `ended`; таймер, который спрашивает, остаётся в окне.
4. `SingleRun.conclude(attempt, job, task) -> Outcome` — один раз на расчёт; повторный вызов возвращает тот же итог и не повторяет побочных действий (строка истории, запись проекта, орбитали). Итог: состояние (`finished` / `failed` / `stopped` / `uncertain`), файлы (`output`, `orbitals`, `path`), что открыть, предупреждения кодами (`optimization_unconverged`, `orbitals_not_made`, `project_not_updated`, `history_not_updated`) с текстами, проблемы, разрешённые действия (`open_result`, `open_steps`, `show_problems`, `check_server`). Сбой записи — предупреждение, не сбой расчёта.
5. `RunTool._finish_job` берёт итог у `conclude` и только показывает его.
6. Строка очереди (шаг C, с 0.108.33): строка расчёта находится по папке его задания (`lifecycle.row_of`), а не как «та, что сейчас идёт»; с 0.108.57 задание, чью папку не знает ни одна строка, ничьё — `None`, а не идущая строка (идущая берётся, только если у неё самой папки нет — запись старше 0.91.7); конец такого задания из папки очереди не записывается ни строке, ни как одиночный расчёт, а отмечается в errors.log; конец строки (`row_ended`) записывается один раз на задание — повторный конец ничего не пишет и не запускает следующую строку второй раз. Неизвестный исход строки — §3c. Переход к следующей строке пока идёт через таймер окна в контексте места (`at_place`) — это ещё не выведено из окна. С 0.108.63 что делать дальше, решает `azimuth/runtime/queue_steps.advance(queue, steps)` по сохранённой очереди без окна: сначала то, что идёт или отправлено на сервере, иначе отправка остатка одним заданием, иначе первая ждущая строка (поиск конформера — один раз за вызов, ошибка запуска — строка `failed` и следующая), конец или остановка; окно даёт шаги (`batch_actions._QueueSteps`: запуск, слежение, показ) и только планирует вызов таймером. Тесты — `tests/runtime/test_queue_steps.py`.

Тесты: `tests/runtime/test_single_run.py` — поддельный расчёт, настоящий проект во временной папке, без Qt и без окна.

**Граница гарантии «один раз»** (0.108.57, уточнение по проверке 2026-11-10). `SingleRun.conclude` и `row_ended` запоминают итог на объекте задания после того, как записи сделаны: повторный таймер того же задания в том же запуске программы ничего не пишет второй раз. Это не транзакция между внешними действиями, историей, проектом и файлами:
- задание, подхваченное после перезапуска, — новый объект; от повторов защищают сами записи — попытка и строка пишутся по своим ID (то же состояние ещё раз ничего не меняет), строка в состоянии `done` заново не запускается;
- прерывание между записями одного конца (проект записан, история — нет) не откатывается; то, что не записалось, сообщается (`project_warning`, errors.log) и не повторяется само.
