# Оптимизация загрузки сайта Azimuth и Атласа

Статус: предложение для разработчика. Изменения ещё не реализованы. Основание: анализ локальной сборки `/Users/me/atlas-site/` и HTTP-заголовков опубликованного сайта `https://www.azimuth-chem.com/`.

## Что уже сделано хорошо

Главная страница сравнительно небольшая: около 37 КБ HTML. Иллюстрация главного экрана уже в WebP, шрифты размещены локально и используют `font-display: swap`. На опубликованном сайте проверенные ответы HTML и WebAssembly приходят со сжатием Brotli; WebAssembly имеет правильный тип `application/wasm`.

В Атласе уже предусмотрены общий расчётный Web Worker для вложенных тем, ограничение количества сохранённых iframe и приостановка анимаций скрытых тем. Эти механизмы следует сохранить.

Наиболее заметные возможности улучшения связаны с объёмом начальной страницы Атласа, запуском расчётной среды и стратегией кеширования. Полный размер папки сайта не равен трафику одного открытия: разные ресурсы загружаются по мере необходимости.

## 1. Вынести поисковый индекс из HTML

**Наблюдение.** `atlas/index.html`, блок `/*SIDX*/`, содержит поисковые данные сразу на трёх языках. Размер HTML – 688 667 байт, встроенного блока – 552 732 байта, около 80%. Все размеры здесь до HTTP-сжатия. Остальной HTML занимает приблизительно 136 КБ.

**Реализация.**

- При сборке создавать отдельные индексы для русского, английского и китайского языков.
- Загружать только индекс текущего языка при фокусе в поиске или первом запросе. Необязательную фоновую загрузку выполнять после появления основного содержимого и с учётом экономии трафика.
- Сохранять Promise загрузки, чтобы повторные действия не создавали одинаковые запросы.
- При переключении языка загружать соответствующий индекс; не показывать результаты устаревшего запроса или прежнего языка.
- При ошибке загрузки показывать понятное состояние и возможность повторить поиск.
- Включать нужный индекс в явное сохранение Атласа для работы без сети.

**Проверка.** При обычном открытии страницы не скачиваются индексы остальных языков. Поиск даёт прежние результаты на всех трёх языках и работает после офлайн-сохранения. Уменьшение HTML примерно в пять раз не следует выдавать за пятикратное ускорение сайта целиком.

## 2. Разделить показ темы и запуск расчётной среды

**Наблюдение.** `atlas/assets/js/qcapi.js` при загрузке запрашивает `health`. В `atlas/assets/js/qcworker.js` обработка любого сообщения сначала вызывает `start()`, поэтому даже проверка готовности запускает Python и NumPy. В просмотренной сборке каталог Pyodide занимает 25 739 772 байта, архив Python-кода – 356 510 байт. Это около 26 МБ файлов до HTTP-сжатия, а не измеренный сетевой трафик конкретного визита.

Механизм готовых ответов уже реализован в `atlas/assets/js/qcstatic.js`, однако текущий индекс содержит только ответы для `aim.stage` и `aim.prof`.

**Реализация.**

- Разделить состояния «страница доступна», «готовые данные доступны» и «расчётный движок готов». Не подменять реальную готовность Python фиктивным успешным `health`.
- На этапе сборки рассчитывать начальные состояния основных демонстраций теми же научными функциями, которые используются при интерактивном расчёте.
- При открытии темы показывать эти данные без обязательной загрузки Python. Текст и навигация также должны работать независимо от запуска движка.
- Запускать общий worker при первом запросе, отсутствующем среди готовых ответов. Для тем без готового состояния сохранять рабочий путь обычного расчёта.
- Показывать отдельный прогресс подготовки движка и последующего расчёта; предусмотреть повторную попытку после сетевой ошибки.
- Привязывать готовые ответы к версии научного кода, параметрам и формату данных. Обновление алгоритмов должно обновлять соответствующие ответы.

**Проверка.** Подготовленная тема открывается с начальными графиками без запросов к Pyodide. Изменение параметров при необходимости запускает движок один раз. Числа и графики совпадают с результатами действующего расчётного кода. Научная точность ради скорости не уменьшается.

## 3. Не задерживать выдачу ответа записью в кеш

**Наблюдение.** В `sw.js` функция `keep()` ожидает завершения `cache.put()` и только затем возвращает ответ странице. Это ставит запись в кеш на путь загрузки ресурса и задерживает потоковую обработку крупных ответов.

**Реализация.** Отдавать сетевой `Response` потребителю сразу, а его копию сохранять параллельно. Продление жизни операции записи оформить через `event.waitUntil()` в рамках обработки события. Ошибка записи, например из-за нехватки места, не должна превращать успешную сетевую загрузку в ошибку страницы. Ответ клонировать до потребления тела; исключить повторное чтение одного потока.

**Проверка.** На медленной сети данные начинают поступать странице до окончания записи в кеш. Повторная загрузка использует сохранённую копию. При искусственной ошибке Cache Storage сетевой ресурс остаётся доступным. Проверить отдельно крупный WASM-файл и обычные HTML/JS.

## 4. Ускорить повторное открытие тем и согласовать обновления

**Наблюдение.** Для HTML, JavaScript и CSS service worker сначала обращается к сети с `cache: 'no-cache'`. Сохранённая копия возвращается при сетевой ошибке. На медленном, но работающем соединении ранее просмотренная тема продолжает ждать сеть.

Кроме того, `IMMUTABLE` задаётся целыми каталогами. В них встречаются постоянные имена, например `pyodide.asm.wasm` и `fonts.css`. При активации новой версии service worker такие файлы переносятся из прежнего кеша. Если содержимое меняется при неизменном URL, старая копия может пережить обновление сайта.

**Реализация.**

- Ввести хеши содержимого в имена ресурсов или версионированные каталоги. Долгое кеширование применять к действительно неизменяемым URL.
- Для таких ресурсов использовать cache-first и подходящие HTTP-заголовки длительного кеширования.
- Для страниц выбрать согласованную стратегию: быстрый показ сохранённой версии с обновлением в фоне либо обращение к сети с ограниченным ожиданием и переходом к сохранённой копии.
- Обновлять HTML и связанные скрипты согласованно: не смешивать несовместимые версии страницы, worker, Python-кода и готовых ответов.
- Учесть, что текущая функция ключа кеша удаляет query-параметры. Добавление только `?v=...` не решает версионирование при такой схеме; предпочтительны хеши в пути или пересмотр правил ключей.
- Не назначать всему сайту бессрочное кеширование. Сохранить предсказуемое обновление служебных манифестов и service worker.
- Согласовать правила браузерного кеша, Cache Storage и хостинга; не включать произвольное кеширование всего домена поверх Cloudflare Pages.

**Проверка.** Уже просмотренная тема быстро открывается на медленной сети и без сети. После выпуска новой сборки пользователь получает согласованный комплект ресурсов. Обновление файла с прежним логическим назначением не оставляет старую копию навсегда. Открытые вкладки переживают обновление без поломки расчётов.

## 5. Вернуть потоковую компиляцию WebAssembly

**Наблюдение.** В `atlas/assets/js/qcworker.js` методы `WebAssembly.compileStreaming` и `WebAssembly.instantiateStreaming` принудительно заменены реализациями через `arrayBuffer()`. Комментарий объясняет это прежним отсутствием правильного MIME-типа. При проверке опубликованного WASM-файла сервер уже возвращал `Content-Type: application/wasm` и `Content-Encoding: br`.

**Реализация.** Использовать штатную потоковую загрузку и компиляцию, совместимую с текущей версией Pyodide. Если запасной путь действительно нужен, включать его только для неподдерживаемого режима или соответствующей ошибки ответа, с корректным повторным использованием либо клонированием потока. Не скрывать произвольные ошибки компиляции повторной загрузкой. Постоянно переопределять глобальные методы WebAssembly не требуется.

Изменение выполнять вместе с пунктом 3: ожидание полной записи ответа в кеш тоже мешает выгоде от потокового режима.

**Проверка.** Первый запуск работает при правильном MIME-типе. Запасной путь проверен отдельно, если сохранён. Сравнивать длительность подготовки движка на одинаковой сети с пустым кешем, а не только повторное открытие с уже скачанными файлами.

## 6. Не накапливать расчёты для устаревших положений ползунков

**Наблюдение.** `QC.live()` в `atlas/assets/js/qcapi.js` не допускает показа устаревшего результата, но сам запрос уже отправлен. Старые расчёты могут продолжать занимать общий worker и задерживать последнее выбранное состояние.

**Реализация.**

- Для каждого независимого интерактивного потребителя хранить выполняемый запрос и последнее ожидающее состояние. Новое состояние заменяет ещё не начавшийся устаревший запрос этого потребителя.
- Очередь размещать до отправки работы в занятый worker: накопленные в его очереди сообщения уже поздно объединять, пока выполняется синхронный Python-код.
- Не объединять разные графики только по имени endpoint: у разных потребителей могут быть независимые параметры и результаты.
- Сохранить защиту от устаревшего результата и явно завершать отменённые Promise согласованным статусом.
- При скрытии или удалении темы убирать её ненужные ожидающие запросы. Не прерывать общий worker ради одного ползунка и не сбрасывать расчёты других тем.
- Где уместно, ограничить частоту отправки запросов, сохранив немедленное визуальное движение самого элемента управления.

**Проверка.** Быстрое движение ползунка не создаёт длинную очередь расчётов промежуточных состояний. Итоговый график соответствует последнему значению. Два разных графика и переход между темами не отменяют нужные запросы друг друга.

## Порядок реализации

1. Зафиксировать исходные измерения для главной страницы, обзора Атласа и нескольких характерных тем.
2. Вынести поисковые индексы из HTML.
3. Убрать ожидание записи в кеш и восстановить потоковую компиляцию WASM.
4. Настроить версионирование ресурсов и повторные открытия из кеша, проверив обновления и офлайн-режим.
5. Добавить готовые начальные состояния демонстраций и отложенный запуск Python.
6. Объединить устаревшие интерактивные запросы до отправки в worker.

Изменения необходимо вносить в исходники и генератор, а затем пересобирать сайт. Папка `atlas-site` содержит результат сборки; ручные исправления в ней могут исчезнуть при следующем запуске генератора. Обнаруженный генератор: `/Users/me/Documents/Azimuth-программа/tools/build_atlas_site.py`. Исходные шаблоны страниц и поискового индекса следует найти по его входным путям.

## Как оценить результат

Проверить отдельно первый визит с чистыми HTTP-кешем и Cache Storage, повторное открытие, переходы между темами, смену языка, офлайн-работу и обновление сборки. Отдельно учитывать отсутствие либо наличие уже активного service worker.

Для каждого сценария записать переданные байты, число запросов, момент появления текста, момент появления первого полезного графика, длительность подготовки Python и задержку от последнего изменения ползунка до результата. Дополнительно проверить длительные задачи главного потока и потребление памяти при последовательном просмотре тем.

Сравнения проводить на одинаковой сети и устройстве, включая телефон и соединение, типичное для студентов. Несколько повторов позволят отличить улучшение от сетевого разброса. Не оценивать интерактивный Атлас только по одной общей оценке Lighthouse: готовность расчётов требует отдельного измерения.

В рамках данного анализа браузерные замеры времени и проверка из сети студентов не выполнялись. Найденные механизмы задержек подтверждены кодом, размеры – локальными файлами, сжатие и MIME-тип – HTTP-заголовками. Конкретное ускорение в секундах пока не установлено.
