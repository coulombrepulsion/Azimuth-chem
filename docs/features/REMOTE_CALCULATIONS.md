# Расчёты на сервере — план

Как Секстант будет запускать расчёты на кластере со SLURM и показывать их так же, как свои: время, этапы, «Вывод программы», «Остановить», результат во вкладке. Каждый пользователь вводит свои данные входа; программа не хранит пароли.

## Исходные условия

- Первый сервер — кластер с очередью SLURM. Рабочую станцию без очереди поддержим заодно: это та же схема без `sbatch`.
- Вход: ключ ssh или пароль; иногда нужны VPN или промежуточный сервер.
- Где на сервере ORCA и другие программы, заранее неизвестно — программа должна их найти сама.
- У каждого свой доступ. Профиль сервера можно передать файлом (адрес, раздел, модули), но без паролей и ключей.

## Первый сервер — лабораторный кластер (со слов пользователя, 2026-10-25)

- Вход: адрес, порт, логин и пароль; перед входом нужен OpenVPN.
- Есть очередь: задача ждёт, если не хватает узлов.
- ORCA установлена в корне; MPI — модулями.
- Расчёт ставится так: сначала `module load run_mpi`, потом лабораторный скрипт `orca.sh` (пользователь пришлёт).
- Значит, кроме обычного `sbatch job.sh`, в профиле нужен режим «свой скрипт отправки»: команда вида `module load run_mpi && orca.sh <входной файл> <процессы>`. Как узнать номер задачи и её состояние — по тому, что печатает и делает `orca.sh`: вызывает ли он `sbatch` и печатает ли «Submitted batch job N», где пишет вывод.
- Пароль: окно пароля один раз за сеанс, дальше все команды идут через одно открытое подключение. OpenVPN программа не включает. Если адрес не отвечает, она скажет «Нет связи с сервером — подключён ли OpenVPN?» и повторит попытку, когда VPN появится.

### Что делает `orca.sh` (прислан 2026-10-25)

- Добавляет `/opt/orca` в PATH и задаёт `RSH_COMMAND` для MPI ORCA.
- `-i <папка>` (или `--input <папка>`) — папка относительно текущей; без флага берётся текущая. Скрипт переходит в неё.
- Свой вывод и ошибки пишет в `<папка>/log.log` и `<папка>/err_log.log`.
- Для каждого `*.inp` в папке **и во всех вложенных** (`find`) запускает `/opt/orca/orca файл.inp > файл.out` в этой папке, по очереди.
- В очередь сам не ставит, номер задачи не печатает: очередь, видимо, даёт `run_mpi` (уточняется). Число процессов не задаёт — их задаёт `%pal nprocs` во входном файле, как Секстант и пишет.

Для Азимута: папка расчёта с одним `input.inp` подходит как есть — `cd <папка расчётов> && module load run_mpi && <команда очереди> orca.sh -i <имя папки>`, вывод — `<имя>/input.out`, его и читаем для хода расчёта. Замечания к скрипту:
- `RSH_COMMAND="/usr/bir/ssh -x"` — опечатка, должно быть `/usr/bin/ssh`; нужно, если ORCA идёт на нескольких узлах;
- без кавычек, поэтому пути с пробелами ломаются — имена папок Азимута без пробелов;
- запускаются и `.inp` во вложенных папках — у Азимута их нет.

## Как устроено

### Расчёт на сервере — тот же Job

Секстант работает с расчётом через `runner.Job`: `start`, `poll`, `running`, `stop`, `elapsed`, `text`, `stdout_text`. `RemoteJob` даёт те же функции, поэтому окно расчёта, песочные часы, этапы, окно вывода и открытие результата не меняются.

1. Входные файлы готовятся локально, как сейчас (`runner.prepare`, проверка исправленного файла, ограничения, NEB).
2. Рядом пишутся `job.sh` — скрипт для `sbatch` — и `job.json`: сервер, папка на сервере, номер задачи, время отправки, состояние.
3. Папка загружается в `<папка расчётов на сервере>/<имя>`, затем `sbatch job.sh` — номер задачи записывается в `job.json`.
4. Раз в 10 с: состояние через `squeue -j <id>`, после окончания — через `sacct -j <id>`. Конец файла вывода подтягивается через `tail -c`, только когда он вырос (`stat -c %s`). Время, этапы, циклы, энергия и окно «Вывод программы» берут его, как сейчас.
5. По окончании скачивается нужное: вывод, `.gbw` и Molden, геометрии (`*.xyz`, `*_trj.xyz`), гессиан, `.engrad`. Временные файлы программы (`*.tmp*`) не скачиваются. Для ORCA на сервере сразу запускается `orca_2mkl` — локальная ORCA для орбиталей не нужна.
6. «Остановить» — `scancel <id>`; без очереди — остановка всей группы процессов.

### Подключение

Используется системный `ssh`/`scp` (macOS, Linux, Windows 10+), а не своя библиотека.

- Сразу работают ключи, `~/.ssh/config`, ssh-agent, ProxyJump и настройки, которые даёт университет.
- Пароль и второй фактор программа спрашивает в своём окне (`SSH_ASKPASS`) и нигде не хранит.
- Чтобы пароль спрашивался один раз, на Mac и Linux одно подключение держится открытым (`ControlMaster`/`ControlPersist`): все `squeue`, `tail` и `scp` идут через него. На Windows такого нет, там пароль спрашивался бы на каждую команду. С 0.89.17 — кнопка «Вход без пароля» в окне сервера: программа создаёт свой ключ (~/.ssh/azimuth_ed25519) и один раз по паролю записывает его на сервер (на Windows пароль вводится в окне ssh), дальше вход по ключу.
- VPN: программа не делает туннель сама (нужны права администратора), но просит OpenVPN Connect подключить выбранный профиль (`--connect-shortcut=<id>`), когда сервер не отвечает, и ждёт до минуты (сделано в 0.63.0, `vpn.py`).
- Ключ сервера при первом входе показывается для подтверждения (`StrictHostKeyChecking=ask` через то же окно), потом сверяется с `known_hosts`.

### Профиль сервера («Расчёт → Серверы…»)

- Название, адрес, пользователь, порт, промежуточный сервер (ProxyJump), файл ключа (необязательно).
- Папка расчётов на сервере (по умолчанию `~/azimuth/calculations` — латиницей, чтобы не зависеть от кодировки сервера).
- Для каждой программы (ORCA, Gaussian, Psi4, xtb, CREST): путь на сервере и строки окружения, например `module load orca/6.0.1 openmpi/4.1`.
  - Сделано в 0.222.16 для программ, которые сервер считает (ORCA, MOPAC, Quantum ESPRESSO, CP2K): `ServerProfile.setups` — строки окружения каждой программы отдельно, в окне — список «Строки окружения для»; общие строки (`setup`) остались для всех задач. Строки программы идут после общих и отменяют поиск программы на сервере (`cluster.setup_for(…, program=…)`).
- SLURM: раздел (partition), аккаунт, лимит времени, память на ядро; дополнительные строки `#SBATCH`.
  - Сделано в 0.216.140: раздел, предел времени, проект (account) и QoS в профиле; другие строки `#SBATCH` пишутся в «Строки окружения» и переносятся в шапку скрипта. Свободные ядра узнаются в указанном разделе (`sinfo -p`). Отдельные расчёты на сервере идут одновременно: идущий отходит в своё окно («Расчёт → Другие расчёты на сервере»).
- Где считать: в папке расчёта или на локальном диске узла (`$TMPDIR` или `/scratch/$USER`) с копированием назад в конце и при остановке (`trap`). Многие кластеры требуют второго.
- Хранится в настройках программы, без паролей. «Экспорт…» / «Импорт…» — файл `.azserver` (JSON), чтобы преподаватель мог раздать шаблон, а студент вписал свой логин.

### «Проверить подключение»

Одна команда на сервере (скрипт-разведчик) отвечает:

- вход работает (и через ProxyJump);
- `sbatch`, `squeue`, `sacct`, `sinfo` есть; разделы (`sinfo -h -o %P`), аккаунты пользователя (`sacctmgr -nP show assoc user=$USER format=account`), лимиты времени разделов;
- **где программы** (их заранее не знаем): `module -t avail`, `module spider orca`, `command -v orca xtb g16 psi4 crest`, поиск в обычных местах (`/opt`, `/usr/local`, `~/orca*`, `~/apps`); для каждой найденной — версия (`orca --version` или строка из вывода);
- свободное место в папке расчётов и квота (`quota -s`, если есть).

Результат — таблица с галочками, как значок и галочка программы в карточке «Запуск расчёта»: выбрали найденное — путь и `module load` записались в профиль.

### Скрипт `job.sh`

Собирается из профиля и настроек Секстанта. Перед отправкой его можно посмотреть и поправить — с той же проверкой, что у входного файла.

```bash
#!/bin/bash
#SBATCH --job-name=az-<формула>-<задача>
#SBATCH --partition=<раздел>
#SBATCH --account=<аккаунт>
#SBATCH --ntasks=<процессы>          # ORCA %pal nprocs
#SBATCH --mem-per-cpu=<maxcore × 1,25> M
#SBATCH --time=<лимит>
#SBATCH --output=slurm-%j.out
<строки окружения: module load …>
cd "$SLURM_SUBMIT_DIR"
"$(command -v orca)" input.inp > input.out 2>&1   # ORCA: полный путь для MPI
orca_2mkl input -molden                          # орбитали для Спектра и Компаса
```

Для других программ — свои строки запуска, те же, что в `runner.prepare`: Gaussian `g16 input.gjf`, Psi4 `psi4 input.dat output.out -n N`, xtb с `OMP_NUM_THREADS`, CREST.

### Расчёт переживает закрытие ноутбука

- `job.json` в локальной папке расчёта — признак незаконченного серверного расчёта. При запуске программа находит такие папки и подхватывает их: песочные часы, окно расчёта, результат во вкладке, из которой расчёт отправлен (если её уже нет — в новой).
- Связь пропала (сон, VPN) — расчёт продолжается на сервере. В окне видно «Нет связи с сервером · последняя проверка 12:40», проверки повторяются через 30 с, 1, 2, 5 минут.
- Панель «История расчётов» в Секстанте: все расчёты молекулы (свои и серверные), статус, время, «Открыть», «Повторить», «Остановить».
- 0.95.0: при запуске Секстант сам спрашивает о незаконченной очереди («Открыть её и следить за ней дальше?» — окно расчёта со всей очередью, как при запуске; расчёт очереди, что шёл на сервере, не отправляется заново, Секстант снова следит за ним) или, если очереди нет, о последнем серверном расчёте без конца («Проверить его?»). «Нет» запоминается для этой папки (`modules/sextant/unfinished.py`).
- 0.222.19: сервер без SLURM — `az-submit.sh` при отсутствии `sbatch` запускает `job.sh` через `nohup` в своей сессии (номер задания — номер процесса, предел времени из `#SBATCH -t` держит `timeout`); состояние и остановка — `cluster.queue_command` / `cluster.cancel_command`; запуск только на свободных ядрах (`cluster.no_room`: по средней загрузке, занято не больше 80 %); очереди туда не отправляются. «Узнать ресурсы» ищет программы и вне PATH (`probe_command(search=True)`).
- 0.96.0: очередь на сервере считается и без программы: при выходе «Отправить и выйти» ставит в SLURM все неотправленные расчёты, каждый ждёт предыдущего (`sbatch --dependency=afterany:N`); при следующем запуске Секстант подхватывает очередь, следит за расчётами по одному и забирает готовые; число процессов берётся из `batch.json`, «Остановить» снимает отправленные (`scancel`).

## Этапы

1. **SLURM, основной путь.** Профиль, `job.sh`, загрузка, `sbatch`, `squeue`/`sacct`, конец вывода, скачивание, `scancel`, `orca_2mkl` на сервере, окно пароля, одно подключение.
2. **«Проверить подключение» и поиск программ** (module, PATH, обычные места), выбор найденного в профиль.
3. **Возвращение к расчётам** после перезапуска, обрыв связи, «История расчётов».
4. **Разное.** Рабочая станция без очереди; локальный диск узла; экспорт и импорт профиля; уведомление по окончании; выбор, что скачивать; несколько расчётов сразу.

## Проверка

- Тесты с поддельными `ssh`, `scp`, `sbatch`, `squeue`, `sacct`, `scancel` — скрипты, которые выполняют всё на этом компьютере и ведут маленькую «очередь» в файле. Проверяются отправка, ход, конец, ошибка, остановка, обрыв связи, возвращение после перезапуска, разбор `job.sh`.
- Разведчик проверяется на записанных ответах `module avail`, `module spider`, `sinfo` и `sacctmgr`.
- Первый живой прогон — на вашем кластере: настоящий сервер отсюда недоступен.

### Ядра: три сервера, у каждого своё число (со слов пользователя, 27 октября)

- В лаборатории **три сервера**, на всех SLURM. Число ядер у них разное, поэтому в профиле оно не хранится: **перед каждым запуском программа спрашивает сервер** (с 0.108.47 — при выборе сервера, рекомендация идёт в поля панели, см. последний раздел) (`cluster.probe_command`: `nproc`, `lscpu`, `/proc/meminfo`, `sinfo -N -o '%N|%c|%m|%e|%C|%t'`, `df -Pk`) и предлагает число процессов по свободным **физическим** ядрам (SLURM может считать потоки) и память на процесс по свободной памяти узла (`cluster.plan`). Оба числа одинаково записываются во входной файл (`%pal nprocs`, `%maxcore`) и в запрос к очереди (`#SBATCH -n`, `--mem`, если SLURM знает память узла).
- Строка в карточке «Запуск расчёта»: «serv3: свободно 40 из 48 ядер, память 251 ГБ, на диске 52 ГБ» (`cluster.summary`). Больше ядер, чем свободно, выбрать можно — с пометкой «встанет в очередь»; больше, чем есть на сервере, — нельзя.
- Ещё нужен вывод `lscpu`, `free -g`, `sinfo -N -o …`, `scontrol show node` с каждого из трёх серверов — проверить, считает ли SLURM потоки и знает ли он память узла.

### Что нужно узнать у лаборатории (до подключения к живому кластеру)

1. Как именно задача ставится в очередь: что делает `module load run_mpi` (только окружение MPI или ещё и очередь); точная команда ручного запуска и **что она печатает** (номер задачи).
2. Какая очередь: SLURM (`squeue`, `sacct`, `scancel`) или другая (PBS: `qstat`, `qdel`); как смотреть состояние и снимать задачу.
3. Видят ли узлы домашнюю папку, или нужно считать на локальном диске узла и копировать назад.
4. Раздел (partition), аккаунт, лимит времени, предел числа задач, квота на диске.
5. Версия ORCA на кластере и есть ли рядом `orca_2mkl`.
6. Можно ли поставить ssh-ключ вместо пароля; бывает ли второй фактор.
7. В `orca.sh` — `RSH_COMMAND="/usr/bir/ssh -x"`, должно быть `/usr/bin/ssh` (для расчётов на нескольких узлах).

Проще всего — вывод трёх команд, выполненных руками: постановка тестового расчёта, просмотр его состояния, снятие задачи.

### Что осталось сделать

**Этап 1 — отправка и ход расчёта (главное).**
- `modules/sextant/ssh.py`: системные `ssh`/`scp`, одно открытое соединение (`ControlMaster`/`ControlPersist`), пароль из окна программы через `SSH_ASKPASS` (маленький помощник, который отдаёт пароль из памяти программы), подтверждение ключа сервера, тайм-ауты, понятные ошибки («нет связи — подключён ли VPN?», «неверный пароль», «ключ сервера изменился»).
- `RemoteJob` с интерфейсом `runner.Job` (`start`, `poll`, `running`, `stop`, `elapsed`, `text`, `stdout_text`) — окно расчёта, анимация Квил, песочные часы, этапы, «Вывод программы» и открытие результата не меняются.
- Два режима отправки: SLURM (`job.sh` из профиля и настроек, можно посмотреть и поправить перед отправкой) и «свой скрипт» лаборатории (команды отправки, состояния и снятия — в профиле; номер задачи — по образцу строки вывода).
- Ход: загрузка папки, постановка в очередь, номер задачи в `job.json`; раз в ~10 с состояние («В очереди», «Идёт», «Готово», «Ошибка») и новый конец вывода (`stat`/`tail -c`).
- Конец: `orca_2mkl` на сервере, скачивание вывода, орбиталей, геометрий, гессиана без временных файлов; результат — во вкладке, из которой отправлен расчёт. «Остановить» — снятие задачи.

**Этап 2 — «Проверить подключение».** Скрипт-разведчик: вход, команды очереди, разделы и аккаунты, где программы (`module avail`, `module spider`, `command -v`, обычные места) и их версии, свободное место. Таблица с галочками; выбранное записывается в профиль.

**Этап 3 — расчёт переживает закрытие ноутбука.** Поиск незаконченных `job.json` при запуске, «Нет связи · последняя проверка …» с повторами через 30 с, 1, 2, 5 мин, панель «История расчётов».

**Этап 4 — остальное.** Рабочая станция без очереди; локальный диск узла; Gaussian, Psi4, xtb на сервере (сейчас ORCA и, с 0.91.39, MOPAC: `job.sh` — одна задача с потоками, `-n 1 -c N`, `OMP_NUM_THREADS` и `THREADS=N` во входном файле); экспорт и импорт профиля (`.azserver`, без паролей); уведомление по окончании; несколько расчётов сразу; Windows с паролем (ключ или paramiko).

### Проверка

- Поддельные `ssh`, `scp`, `sbatch`, `squeue`, `sacct`, `scancel` — скрипты, выполняющие всё локально и ведущие «очередь» в файле: отправка, ход, конец, ошибка, остановка, обрыв связи, возвращение после перезапуска.
- Первый живой прогон — на кластере лаборатории, вместе: отсюда настоящий сервер недоступен.

Этап 1 можно начинать сразу на поддельном сервере; подключение к кластеру — после ответов на пункты 1–3.

## Очередь одним заданием (0.106.6)

Пользователь 2026-11-08: «Сделай чтобы пакетные расчеты шли через что-то подобное [orca.sh], чтобы при выходе из программы
не требовалось загружать все в очередь».

- При запуске очереди на сервере все её расчёты готовятся сразу (входные файлы с `%pal`/`%maxcore` по выбранным
  процессам), их папки загружаются, а рядом — папка `<очередь>-batch` со скриптом `batch.sh` (`cluster.batch_script`).
  Один `sbatch batch.sh` — одна задача SLURM, которая, как `orca.sh` лаборатории, считает их по порядку.
- Каждый расчёт оставляет в своей папке метки: `.az-started` (время начала), `.az-finished` (код выхода). Расчёт с
  `.az-finished` не повторяется — тот же скрипт, отправленный ещё раз, продолжит с места остановки.
- Азимут следит за расчётами по одному (`BatchItemJob`): ждёт метку начала, копирует растущий вывод, по метке конца
  скачивает результат. После перезапуска программы слежение подхватывается по `job.json` (в нём `"batch": true` и
  общий номер задачи).
- «Пропустить» — файл `.az-skip` в папке расчёта: скрипт завершает группу процессов ORCA (`setsid`, `kill -- -pid`) и
  переходит к следующему. «Остановить» — `scancel` общей задачи.
- При выходе отправлять нечего. Очередь, в которой сначала ищутся конформеры (поиск идёт на этом компьютере между
  расчётами), по-прежнему отправляется по одному.

## Отправка одним архивом и ресурсы в панели (0.106.9, 0.108.47, 0.108.52)

- Очередь уходит на сервер одним архивом (`ssh.Connection.upload_packed`): один `scp` tar.gz и одна команда ssh, которая
  распаковывает его и ставит `batch.sh`, — время отправки не растёт с числом расчётов.
- Число процессов и память больше не спрашиваются окном перед запуском. При выборе сервера Секстант опрашивает его
  (`cluster.probe_command`, как выше) и ставит рекомендацию в поля «Процессы» и «Память» панели (`apply_server_resources`),
  при возврате на компьютер — рекомендацию компьютера. Расчёт и очередь берут значения панели:
  `cluster.plan(resources, wanted=cores, maxcore=memory)`; что может задержать задачу в очереди SLURM, сказано строкой
  (`notify_server_plan`). MOPAC на сервере получает то же число как потоки (`-n 1 -c N`, `THREADS=N`).
- Поля, изменённые вручную после выбора сервера, рекомендацией не заменяются (0.108.52); выбор сервера заново
  сбрасывает этот признак.

## Сервер недоступен, задача пропала из очереди, конец дважды (0.108.61, T09–T11)

- **Последний ответ сервера.** В папке расчёта `observed.json` — последнее увиденное состояние и время. При подхвате и
  при обрыве связи окно расчёта пишет «последний ответ сервера — 14:02 10.11, шёл». Подхват очереди, у которой всё уже на
  сервере, и «Проверить на сервере» больше не обрываются ошибкой, если сервер не отвечает: слежение начинается и само
  ждёт связи (`server_access.open_for_watching`).
- **Задачи нет в squeue.** Успех — только по отметке нормального конца в выводе. Без отметки задача считается
  законченной после трёх ответов подряд «нет в очереди», пока вывод не растёт (`remote_job.GONE_CHECKS`); конечные
  состояния SLURM (COMPLETED, FAILED, CANCELLED, TIMEOUT…) в ответе squeue — тоже «нет в очереди».
- **Конец дважды.** Уже записанный конец расчёта или строки очереди не записывается снова, орбитали и расчёты BSSE не
  повторяются.

## Файлы результата приходят только целыми (0.108.62, T16)

Файлы результата скачиваются сначала во временную папку `.az-transfer` в папке расчёта и переносятся в неё, только
когда размер совпал с тем, что сообщил сервер (`wc -c`). Оборванная передача и короткая копия повторяются (до трёх
раз); файл, который так и не пришёл целым, в папку не попадает и не заменяет прежний — окно называет его, а он остаётся
на сервере.

## Очередь на сервере — один взгляд на всю группу (0.108.69)

Наблюдатели расчётов очереди одним заданием спрашивают сервер одной командой на всю группу
(`remote_job.group_command`): состояние общего задания в squeue и отметки `.az-started`, `.az-finished`, `.az-skip` всех
папок из `group.json`. Ответ общий: следующий расчёт очереди, подхваченный после конца предыдущего (или по одному после
перезапуска, когда сервер успел посчитать многое), берёт ответ моложе интервала опроса, а не спрашивает заново.
