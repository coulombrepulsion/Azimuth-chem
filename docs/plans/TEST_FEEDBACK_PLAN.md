# Azimuth: быстрые проверки при разработке и полный контроль перед выпуском

Предложение и план реализации для разработчика. Статус: **к реализации**; перечисленные ниже новые команды и профили пока не реализованы этим документом.

Основание: запрос владельца о длительных тестах; просмотр кода и настройки тестов Azimuth 0.138.5. Документ описывает изменение организации проверок, не научных алгоритмов программы. Согласно текущему AGENTS.md, такая внутренняя работа не требует новой версии, записи CHANGELOG или заметки Квил. Полный прогон владельца перед push и проверки выпуска сохраняются.

## 1. Проблема и ожидаемый результат

После небольшой правки разработчику нужна быстрая проверка изменённого поведения и связанных сценариев. Запуск всего набора после каждого промежуточного изменения задерживает обратную связь. При этом сокращённый набор не должен выдаваться за полную проверку программы.

В сохранённом тогда `pytest.log` (прогон 2026-11-08; файл удалён 2026-11-24 как устаревший) указан результат: **1711 passed, 9 skipped за 409,94 секунды (6 минут 49 секунд)**. Этот файл не содержит достаточных сведений, чтобы приписывать время текущему коммиту или считать его воспроизводимым базовым замером. Нужно измерить текущую версию на фиксированной машине и отдельно учесть сбор тестов, подготовку, выполнение и очистку.

Целевой результат:

- несколько понятных команд для короткого, тематического и полного прогона;
- живой прогресс, видимые паузы и сохранённые отчёты;
- устранение измеренных лишних затрат без удаления полезных сценариев;
- явный список проверенного и не проверенного в каждом отчёте;
- полный набор и проверка независимости групп остаются обязательными на соответствующих этапах разработки.

Предварительные ориентиры на машине разработчика: короткая проверка до 30–60 секунд, тематическая до 1–3 минут. Это цели для обсуждения после замера, а не обещанные результаты. Полный набор не сокращается ради произвольного лимита времени.

## 2. Что обнаружено в текущем коде

| Место | Наблюдение | Что делать |
|---|---|---|
| `tests/README.md` | Описан прежде всего запуск всего набора | Добавить уровни проверок, команды и правила выбора |
| `pytest.ini` | Есть пути и фильтр предупреждений; профилей быстрого запуска нет | Зарегистрировать семантические маркеры, не менять смысл обычного полного запуска |
| `tools/run_test_groups.py` | Каждая группа запускается отдельно, последовательно | Сохранить проверку изоляции; не считать её быстрым профилем |
| Тот же файл | `subprocess.run(capture_output=True)` скрывает вывод до завершения группы | Показывать начало группы, текущий прогресс, прошедшее время и полный лог при ошибке |
| Тот же файл | Код pytest 5 («ничего не собрано») допускается как успех | Для обязательного непустого профиля считать это ошибкой настройки; допустимые пустые группы отмечать отдельно |
| `tests/gui_support.py` | Помимо фикстур содержит пять функций `test_*`; GUI-модули используют `import *` | Проверить повторный сбор по исходным функциям и параметрам, затем оставить каждому сценарию одно каноническое место |
| `tests/conftest.py` | Уже есть защита от модальных окон, изоляция настроек и удаление оставленных окон | Сохранить; измерять стоимость setup/teardown и проверить отсутствие роста числа живых окон |
| `.github/workflows/tests.yml` | Полный pytest на Windows и Linux, тайм-аут задачи 45 минут; с 0.222.26 запускается вручную и без macOS (бесплатные минуты закрытого репозитория кончились; на Mac полный прогон идёт перед каждым коммитом) | Сохранить полную матрицу; добавить отчёты и отдельный быстрый сигнал, не заменяя им выпускные проверки |

Повторный импорт пяти функций – конкретная гипотеза лишних запусков, а не установленная главная причина всей задержки. Подтвердить её сбором тестов. Число тестовых функций в исходниках, число собранных экземпляров с параметризацией и число уникальных сценариев – разные показатели.

## 3. Профили запуска

Расширить существующий инструмент групп либо добавить единый `tools/test.py`, использующий общие функции обнаружения и запуска. Не создавать два независимых списка состава тестов. Ниже целевой интерфейс нового инструмента, а не доступные сейчас команды.

```text
python tools/test.py quick
python tools/test.py area projects
python tools/test.py area sextant
python tools/test.py full
python tools/test.py isolated
python tools/test.py profile
python tools/test.py affected --base <explicit-base-ref> --dry-run
```

Запускать тем интерпретатором, в котором установлены зависимости проекта: `.venv/bin/python` на macOS, `.venv\Scripts\python.exe` на Windows. Внутренний runner использует `sys.executable`, список аргументов и корень репозитория как cwd.

| Профиль | Состав | Когда применять |
|---|---|---|
| `quick` | Небольшой явный набор критических проверок данных, входов, сохранения и чтения; несколько необходимых UI-сценариев | После небольшого изменения как первый сигнал |
| `area NAME` | Тесты области, её публичных зависимостей и взаимодействия с UI | Основная проверка конкретной задачи |
| `full` | Весь обычный набор без неявного исключения медленных тестов | Перед push по правилу владельца, после широких изменений и перед выпуском |
| `isolated` | Каждая группа в отдельном процессе, как в существующем инструменте | После изменений фикстур, общих настроек, порядка импортов и на контрольных этапах |
| `profile` | Полный последовательный прогон с подробными временами и метаданными среды | До оптимизации и после изменения конкретного узкого места |
| `affected` | Предложение набора по изменённым файлам с объяснением причин | Удобство разработчика; не доказательство полноты покрытия |

`quick` – явный список или зарегистрированный маркер, а не «всё без slow». Иначе новый тест случайно увеличит короткий набор или важный медленный сценарий исчезнет из проверок. Объём выбранного набора всегда печатается до запуска.

## 4. Первый этап: измерение и наблюдаемость

Сначала провести один контрольный последовательный прогон на текущем HEAD. Сохранить коммит, dirty-состояние, версию Python/pytest, ОС, CPU, число workers, версии Qt/VTK, режим графики, настройки потоков численных библиотек, точную команду и коды завершения. Не включать секреты, настройки настоящего сервера и содержимое пользовательских проектов.

Команда, доступная уже сейчас, из корня программы; каталог отчёта предварительно создать:

```bash
python -m pytest tests -q -ra -p no:cacheprovider \
  --durations=30 --durations-min=0.05 \
  --junitxml=artifacts/tests/baseline/junit.xml
```

На Windows это та же команда в одну строку. Режим Qt и VTK фиксировать и включать в описание среды: результаты offscreen и настоящего OpenGL не смешивать. Отключение VTK не считается успешной проверкой VTK.

Для отчёта по фазам добавить маленький pytest-плагин, подключаемый runner через `-p`. Через `pytest_runtest_logreport` собирать `nodeid`, `when`, `duration`, `outcome`, сведения о skip/xfail и worker. Сбор и полный wall-clock измерять отдельно. Зафиксировать, что в параллельном режиме сумма длительностей тестов не равна времени ожидания пользователя. JUnit XML дополняет этот отчёт, но не заменяет подробные данные о фазах.

Предлагаемая запись отчёта:

```json
{
  "profile": "area:projects",
  "git_commit": "...",
  "dirty": false,
  "workers": 1,
  "wall_seconds": 52.4,
  "collection_seconds": 3.1,
  "selected_count": 80,
  "deselected_count": 0,
  "exit_code": 0,
  "tests": [
    {"nodeid": "tests/projects/test_example.py::test_example",
     "phase": "setup", "seconds": 0.21, "outcome": "passed"}
  ]
}
```

Значения и путь теста здесь иллюстративные, не результаты замера. Для сравнения оптимизации провести три последовательных запуска до и после на одинаковом наборе и окружении, показать медиану и разброс. Не повторять весь набор после каждой мелкой правки измерителя; сначала проверить измеритель на небольшом искусственном наборе.

## 5. Второй этап: понятный прогресс и диагностика зависаний

Для `run_test_groups.py` заменить накопление всего вывода до конца на `Popen` с потоковым чтением. Сохранять stdout/stderr в файл и показывать состояние в терминале. Учитывать, что дочерний процесс может буферизовать stdout: использовать `python -u`/`PYTHONUNBUFFERED`, события плагина или безопасный канал сообщений. Чтение потока не должно блокировать таймер обновления статуса; пригоден отдельный читающий поток и очередь сообщений, совместимые с Windows.

Перед каждой группой выводить её имя и время начала, во время работы – счётчик и прошедшее время. Для очень долгого теста печатать последнее известное `nodeid` и фазу; обновлять служебное сообщение примерно раз в 10–15 секунд, если новых событий нет. Это сообщение подтверждает работу runner, но не доказывает, что сам тест не завис.

Нужны три разных механизма: общий предел времени профиля, диагностический порог отдельного теста и жёсткое прекращение действительно зависшего процесса. Пороги назначать по измерениям с запасом; медленную научную проверку не обрывать произвольным коротким лимитом. Перед принудительной остановкой по возможности сохранять стек и последние события. Тайм-аут никогда не возвращает успех.

При Ctrl+C и тайм-ауте завершать только дочерние процессы данного прогона, сначала мягко, затем жёстко после ограниченного ожидания. Проверить этот механизм отдельно на macOS и Windows. Не оставлять тестовые серверы, поддельные расчётные процессы и Qt-процессы после завершения runner.

При падении группы показывать исходный код завершения, путь лога и содержательную ошибку. Текущее извлечение только строк `FAILED`/`ERROR` недостаточно для аварии нативной библиотеки или ошибки импорта. Прерванный, аварийный и пустой прогоны должны отличаться от успешного.

## 6. Третий этап: убрать лишние затраты

### 6.1. Повторный сбор тестов

Собрать GUI-тесты без выполнения, получить список `nodeid` и адрес исходной функции: модуль, qualified name, файл и строку определения, параметры. Одинаковые имена в разных файлах не являются достаточным признаком дубликата; разные параметры сохраняют отдельные сценарии.

Функции `test_*` из `tests/gui_support.py` перенести в подходящий канонический тестовый модуль. В support оставить только помощники; фикстуры, используемые разными модулями, при необходимости перенести в ближайший общий conftest. Не переносить весь набор фикстур в корневой conftest без нужды: это может увеличить стоимость сбора всех тестов.

Заменять `import *` постепенно явными импортами либо определить строгий публичный список помощников. Проверить, что число копий снизилось, а каждый уникальный сценарий, параметризация и ожидаемый результат сохранились. В отчёте показать точное соответствие старых и новых node IDs.

### 6.2. Стоимость окна и фикстур

Измерить создание `Studio`, применение темы, подготовку модели и удаление окна. Тесты парсеров, геометрии, сериализации и правил состояния по возможности выполнять через чистые интерфейсы без Qt. Для реальных UI-проверок сохранить настоящее окно.

Не переводить изменяемое окно в session scope ради ускорения: это создаёт зависимость тестов от предыдущего состояния. Допустимо переиспользовать неизменяемые эталонные данные и безопасную инфраструктуру, но настройки, проекты, файлы и рабочее состояние теста должны быть изолированы. Тестирование отклика реального окна не заменять заглушкой самого окна.

Сохранить текущую очистку `windows_of_the_test`. Проверить не только её стоимость, но и отсутствие нарастания памяти, числа окон, таймеров и фоновых потоков при повторном прогоне GUI-группы.

### 6.3. Ожидания и внешние программы

Найти фиксированные sleep и ожидания событий; оптимизировать те, которые попали в список длительных проверок. Для UI ожидать конкретное событие/состояние с ограничением времени. В тестах политики повторных подключений управлять часами и имитировать транспорт; не ждать настоящие минуты backoff.

По умолчанию тесты не должны незаметно запускать установленную ORCA, настоящий SSH-сервер или полный тяжёлый Multiwfn-анализ. Такие интеграционные проверки выделить и запускать явно в подготовленной среде. При этом тесты парсеров должны продолжать читать реальные эталонные выводы и сравнивать научные величины с независимыми значениями.

## 7. Маркеры и соответствие изменений тестам

После инвентаризации зарегистрировать маркеры, например:

```ini
markers =
    smoke: короткий критический сценарий
    gui: требуется настоящее окно Qt
    native_graphics: требуется поддерживаемый OpenGL/VTK
    external_program: запускается настоящая внешняя расчётная программа
    network: требуется реальное внешнее соединение
    serial: сценарий не допускает параллельного выполнения
    slow: высокая измеренная стоимость, с указанной причиной
```

Это дополнение к существующему `pytest.ini`, не его полная замена. Маркеры `external_program` и `network` не означают разрешение обращения к реальным ресурсам. Отдельный профиль должен требовать явного подключения соответствующей среды. Неподдерживаемые возможности фиксируются как skip с причиной; обычные регрессии не переводятся в skip/xfail для получения зелёного результата. После регистрации включить проверку неизвестных маркеров.

Предварительная карта тематических профилей, которую уточнить по реальным зависимостям:

| Изменение | Обязательная область проверки |
|---|---|
| Модель проекта, Session, Repository, миграции | Проекты, сохранение/восстановление, импорт/экспорт, запуск, повтор, получение результата |
| Очередь или удалённый расчёт | Секстант, запись попыток, повторное подключение, работа с проектом, связанные GUI-сценарии |
| Парсер результатов | Парсер на эталонах, общая модель результата, свойства и соответствующие проверки Спектра |
| Редактирование/геометрия | Компас, ввод/вывод форматов, сохранение структуры проекта, соответствующие UI-сценарии |
| Переводы/общая тема/виджеты | Core и затронутые интерфейсные группы; общая тема требует широкого UI-прогона |
| Корневой conftest, зависимости, сборка, runner | Сбор всех тестов, полный набор и отдельные группы |
| Документация | Проверка ссылок и форматирования; полный pytest не нужен, если нет исполняемых изменений |

Для `affected` база сравнения задаётся явно или выводится с объяснением. Учитывать staged, unstaged, новые файлы, удаления и переименования. Неизвестный путь или изменение общего компонента должно расширять выборку либо требовать решения разработчика, а не давать пустой успех. Автоматическая карта не знает всех динамических зависимостей; профиль не заменяет полный прогон перед push.

## 8. Параллельность – только после измерения и изоляции

Сначала убрать дубли, лишние окна и искусственные ожидания. Затем проверить `pytest-xdist` на чистых независимых тестах с двумя workers, после этого с четырьмя. Добавление зависимости проводить по правилам проекта. Не включать `-n auto` всему набору по умолчанию: несколько Qt/VTK-процессов и численных библиотек могут увеличить нагрузку, память и время.

Для каждого worker нужны независимые настройки, временные папки, проекты, порты и логи. Ограничить суммарное число потоков BLAS/OpenMP при необходимости; значения фиксировать в отчёте. Порядок и количество собранных тестов должны совпадать у workers, как требует xdist. Случайная параметризация должна быть детерминированной.

Serial и native-graphics проверки запускать отдельным последовательным вызовом. Один маркер `serial` сам по себе не заставляет xdist выполнять тест последовательно. Полный профиль должен объединять результаты всех частей, сохранять состав собранного набора и завершаться ошибкой при провале любой части. Ускорение признаётся только при одинаковом наборе сценариев и приемлемом пике памяти.

## 9. CI и правила разработчика

Короткие проверки дают быстрый предварительный сигнал. Полная матрица macOS/Windows остаётся окончательной проверкой соответствующего этапа. Текущий AGENTS.md требует полного прогона владельца перед push; этот документ не отменяет правило. Для выпуска остаются также проверки установки и необходимых внешних программ.

В CI сохранять summary JSON, JUnit XML, полные логи, выбранные node IDs и сведения об окружении даже при падении или тайм-ауте. Отмечать причины пропуска, графический режим и доступность внешних программ. Тайм-аут CI – защита от зависания, не допустимая нормальная длительность тестов.

Минимальная дисциплина после изменения: сначала релевантный тест, затем тематический профиль. После успешного результата повторять тот же прогон только при новых правках или конкретном подозрении на нестабильность. Перед обязательной полной проверкой рабочая копия фиксируется: нельзя приписывать результат другому коммиту или набору изменённых файлов.

## 10. План поставки и критерии готовности

1. **Инструментирование:** измерение фаз и времени сбора, метаданные среды, логи и живой прогресс. Приёмка: искусственно медленный тест виден; ошибочный импорт, пустой набор, Ctrl+C и аварийное завершение дают правильный итог.
2. **Канонический сбор:** проверить и убрать повторный сбор support-тестов. Приёмка: ни один уникальный сценарий не потерян, каждая группа собирается и выполняется самостоятельно.
3. **Профили:** реализовать quick/area/full/isolated/profile, карту выбора и документацию. Приёмка: `--dry-run` показывает состав; неизвестная область и обязательный пустой профиль завершаются ошибкой; full охватывает весь заявленный набор.
4. **Измеренные оптимизации:** исправить несколько самых дорогих мест. Приёмка: таблица до/после на одинаковом наборе, результаты и изоляция сохранены; изменения научной точности ради скорости не допускаются.
5. **Выборочная параллельность:** включать только при подтверждённом выигрыше. Приёмка: нет пересечения файлов/настроек, нет новых нестабильных падений, ресурсы не превышают согласованный бюджет.
6. **Интеграция в CI:** отчёты всех частей и понятный итог. Приёмка: падение любой обязательной части делает итог красным; ускоренный профиль нигде не назван полным.

Разработчик передаёт изменения в runner/плагине, `pytest.ini`, `tests/README.md` и CI, точную карту профилей, результаты замеров и перечень оставшихся дорогих тестов с причинами. Для runner использовать небольшие искусственные тестовые наборы; не проверять runner многократным запуском всей научной программы.
